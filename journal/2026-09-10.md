# 2026-09-10 개발 일지

## 서른두 번째 업데이트 — "칼선 작업이 배경만 잡고 있어": 재단선 격자 한 칸에 캐릭터가 여러 개 흩어져 있는 밤하늘 배경 시트에서, 개별 요소 사전 분리를 두 안전장치와 함께 다시 켬

**요청**: 화면 캡처 여러 장과 함께 4가지 피드백을 받음 — 1) 칼선 작업이 배경만 잡고 있음, 2) 칼선이
옆 칼선이랑 붙어 있거나 아예 인식했던 요소를 인지하지 못함, 3) 여전히 잠옷 모자를 인식하지 못하고
도무송도 안이 아니라 밖으로 향해 있어 칼선이 점점 우글거림, 4) 칼선의 정석적인 예시 파일을 보여주며
학습하라는 요청. 정석 예시 파일과, 문제가 재현되는 실제 작업 파일 2개(밤하늘 배경 시트, 이전에 검증해둔
캐릭터 다수 배치 시트)를 받음.

**0) 정석 예시 학습**: 받은 예시 파일을 스크래치 폴더에서만 열어 확인. 실제 작가가 그려둔 칼선(마젠타)이
도안 실루엣을 아주 타이트하고 일정한 간격으로 감싸며, 테두리의 물결/꽃무늬 디테일까지 뭉개지 않고
따라가고, 바로 옆에 붙어 있는 도안끼리도 서로 합쳐지지 않고 각자 따로 칼선이 생기는 것을 확인함 —
이후 재현 검증의 "정답 기준"으로 계속 사용.

**1) 재현 — 밤하늘 배경 시트로 "배경만 잡힘" 직접 확인**: 받은 실제 파일의 재단선 격자 한 칸(캐릭터
여러 개 + 흩날리는 꽃잎/달/나무 등 장식이 배경 가득 깔려 있는 구성)을 기존 방식(칸 전체를 통째로
GrabCut에 넘김)으로 그대로 돌려보니, 실제로 캐릭터들은 전부 놓치고 칸의 거의 전체(핑크색 나무/벚꽃
장식이 있는 모서리를 뺀 나머지 전부)가 하나의 큰 배경 덩어리로 칼선 잡히는 것을 실측으로 확인함 —
캡처와 정확히 같은 증상.

**2) 원인**: 이 파일처럼 칸 안 배경이 하늘/달/별 그림으로 가장자리까지 꽉 채워져 있으면, GrabCut에
"이 칸 전체가 확률적 전경"이라고 알려줘도 칸 내부에서 진짜로 서로 떨어진 캐릭터 여러 개를 가를 색
차이 신호를 찾지 못해 사실상 칸 전체(혹은 그중 제일 눈에 띄는 덩어리)를 그냥 하나로 잡아버림. 이건
이미 2026-09-08(11차)에 한 번 확인되고 되돌려졌던 것과 같은 근본 원인.

**3) 이번에 다시 켠 방법**: `core.multi_design.detect_sub_element_boxes_px`(칸 안에서 선/색 경계로
낱개 요소를 미리 찾는, 이미 만들어져 있었지만 안전하지 않다고 판단해 연결이 끊겨 있던 함수)를
`gui.app._expand_grid_cells_into_sub_elements`를 통해 다시 연결했다. 예전엔 "2개 이상 찾으면 무조건
쪼갠다"였는데, 이번엔 실제 파일로 정확히 재현되는 예전 회귀(카드형 도안 한 장 + 테두리를 두른 작은
장식 여러 개를, 장식 하나하나를 별도 도안으로 오인해 쪼개버리는 것 — 실측: 실제 카드 한 장이 8개로
쪼개짐, 원래 칼선은 1개)를 막기 위해 안전장치 두 개를 추가:

  1. 최소 5개 이상 찾았을 때만 쪼갠다(2개 -> 5개, 훨씬 보수적).
  2. 새 함수 `core.multi_design.is_decorative_frame_cluster`로 "찾은 조각 대부분이 서로 거의
     똑같은 크기의 작은 조각(카드 테두리 장식 패턴)"인지 확인해, 그렇다면 쪼개지 않는다.

**4) 검증(두 실제 파일의 실제 칼선 레이어를 정답으로 대조)**: 두 파일 모두 작가 본인이 그려둔 진짜
칼선 레이어가 있어서, 그걸 정답으로 놓고 직접 대조함(재단선 격자마다 실제 칼선 개수 대 감지된 낱개
요소 개수 비교).
  - 밤하늘 배경 시트: 캐릭터/장식이 흩어진 칸 7개 모두 정확히 쪼개짐(실제 칼선 11~15개 대비 감지
    11~15개, 카드가 하나도 없는 빈 칸 2개는 그대로 0개 유지) — 기존엔 이 7개 칸 전부가 통째로 하나의
    거대한 배경 덩어리였던 것에서 큰 개선.
  - 카드형 요소가 섞인 칸(같은 "꽃 테두리 + 토끼 카드" 디자인이 두 파일에 공통으로 있었음): 두
    안전장치 덕분에 실제 칼선 1개와 일치하게 쪼개지 않고 그대로 유지됨(회귀 없음, 예전 문제 재현
    안 됨).
  - 이미 검증해둔 다른 실제 파일(캐릭터 다수 배치 시트)의 나머지 칸(캐릭터끼리 서로 맞닿아 있어
    5개 미만만 감지되는 칸들)은 최소 5개 기준에 걸려 안전하게 기존 동작(칸 전체 그대로) 유지 —
    새로운 회귀 없음.
  - 실제로 segment_design_in_region까지 전체 파이프라인을 끝까지 돌려서(개별 요소별 실루엣 추적)
    최종 결과도 눈으로 확인: 캐릭터/달/꽃잎 각각 제 모양대로 칼선이 생기는 것을 확인함. 다만 일부
    요소(배경과 색이 비슷한 창문+캐릭터 조합 등)는 실루엣이 실제보다 다소 작게 잡히는 정밀도 문제가
    남아있음 — 이건 이미 알려진 4번(배경과 색이 비슷한 부분이 실루엣에서 덜 잡히는 문제, 아직 미해결)
    과 같은 종류의 별개 문제로, 오늘 새로 생긴 회귀는 아님.

**5) 아직 남은 것**:
  - **2번(칼선이 붙거나 인식 못 함)**: 캡처에 나온 라쿤/타이거 패턴 시트는 아직 실제 파일을 못 받아서
    재현하지 못함 — 받으면 이어서 진행.
  - **3번(잠옷 모자 미인식 + 도무송 방향)**: 이 부분이 보이는 캡처를 아직 못 받아서(받은 캡처 3장은
    전부 1번 증상), 재현하지 못함 — 특히 도무송은 위 3)의 확장 자체를 의도적으로 건너뛰는 작업
    종류라(칸 하나 = 도무송 도형 하나가 도무송의 정의라서), 이번 수정과 무관하게 별도로 봐야 함.
  - 4번(정석 예시 학습)은 완료 — 위 0) 참고.

**검증**: 회귀 테스트 재실행(이 작업 환경에 tkinter가 없어 못 돌리는 GUI 연동 테스트 몇 개는 제외) —

## 서른세 번째 업데이트 — "2번(칼선이 붙어 있거나 인식 못 함)" 재현/원인 규명은 완료, 안전한 수정은
아직 못 찾아 코드는 원래대로 되돌림(회귀 없음)

**요청**: 서른두 번째 업데이트에서 못 받았던 라쿤 무늬 패턴 시트(캡처 2/3/5번에 나온 것)를 실제 파일
8개 중에서 찾아달라는 요청과, "찾는 김에 칼선 깔끔하게 정리하는 법 연구해달라"는 요청을 함께 받음.

**1) 파일 찾기**: 8개를 전부 스크래치 폴더에서만 렌더링해서 눈으로 확인 -- 이미 검증해둔 밤하늘
시트/캐릭터 다수 배치 시트와 같은 파일 2개, 이전에 "이거?" 하고 확인 요청받아 아니라고 답했던 파일과
같은 파일 1개, 처음 보는 새 시트 4개(그중 하나가 캡처와 일치하는 줄무늬 얼굴/체크무늬 원단/잎 모양
장식이 있는 라쿤 무늬 시트임을 확인) + 카드형 도안 1개(토끼 + 꽃무늬 액자, 서른두 번째 업데이트에서
이미 다룬 "카드 + 테두리 장식" 패턴과 같은 디자인이 여기도 있었음).

**2) 재현**: 이 라쿤 무늬 시트도 작가 본인이 그려둔 진짜 칼선 레이어가 있어서, 그걸 정답으로 대조.
캐릭터/장식이 배경 두 가지 색(위/아래 구역)으로 나뉜 칸 하나를 기존 방식(서른두 번째 업데이트에서
다시 연결한 "칸 안 개별 요소 사전 분리")으로 돌려보니: 정답은 낱개 요소 12개인데 실제로는 3개로
뭉개짐(그중 하나가 캐릭터 2~3개 + 장식 1개를 한 번에 담은 거대 블록) -- 정확히 2번 피드백("칼선이
옆 칼선이랑 붙어 있거나 아예 인식했던 요소를 인지하지 못해")과 일치하는 증상을 실측으로 재현함.

**3) 원인**: 배경이 두 색으로 나뉘어 칠해진 경계선이, 색 차이가 아주 옅어서 낱개로는 Canny 엣지가
드문드문(가로 한 줄에 몇십 개 점 정도만) 잡히지만, 이미 있는 "끊어진 선 잇기"용 살짝 팽창/닫기
단계를 거치면서 그 드문 점들이 이어져 가로로 화면 전체를 가로지르는 하나의 벽처럼 작동해버림. 그
벽 + 근처 도안 몇 개의 외곽선이 우연히 맞물리면, "가장자리에서 못 닿는 안쪽은 도안의 구멍으로 보고
채운다"는 기존 알고리즘(`_fill_enclosed_regions`)이 그 벽 안에 같이 들어있던 서로 다른 캐릭터
여러 개의 사이 배경(원래는 뻥 뚫린 빈 공간)까지 통째로 하나의 거대한 전경 덩어리로 잘못 채워버림.
이건 이전 항목들(1번, 4번)과는 다른, 배경 자체의 색 구역 나눔에서 오는 별개의 원인.

**4) 시도한 수정과 각각의 실패 이유(둘 다 실제 파일로 검증하다가 기각)**:
  - **안 채울 영역의 면적 상한선**: "닿지 못한 영역"을 크기별로 나눠, 칸 면적의 일정 비율보다 큰
    것만 안 채우게 해봄 -- 이 라쿤 시트에서는 효과가 있었지만(3개 -> 8개, 실제 캐릭터 7~8개를 거의
    다 개별로 잡음), 서른두 번째 업데이트에서 이미 안전하게 지키고 있던 "카드 + 테두리 장식" 케이스를
    실제로 되돌려 검증해보니 회귀가 발생함 -- 카드 자체가 칸의 상당 부분(약 28%)을 차지하는 큰
    도안이라, 같은 면적 상한선에 걸려 카드 몸통 내부 채우기 자체가 막혀버리고, 카드가 작은 조각
    여러 개로 쪼개져서 "카드+장식 패턴" 감지(`is_decorative_frame_cluster`)가 더 이상 작동하지 않게
    됨(실측: 원래 안전하게 1개로 유지되던 카드 칸이 12개로 잘못 쪼개짐). 즉 이 기준(면적 비율)은
    파일마다 "정상적인 도안 하나 몸통 크기"의 기준이 달라서 일반화가 안 됨.
  - **닿는 외곽선 개수 기준**: "안 채울 영역"이 서로 다른 도안 외곽선 여러 개에 동시에 닿아 있으면
    안 채우게 해봄(진짜 도안 하나의 구멍은 그 도안 자기 외곽선 하나에만 닿아야 정상이라는 논리) --
    라쿤 시트에서는 그 흐릿한 배경 경계선이 다닥다닥 실측상 이미지 전체 폭에 걸쳐 하나의 거대한
    "엣지 뭉치"로 연결돼 있어서(실측: 팽창/닫기 후 이 배경 경계선 하나가 벌써 칸 전체 크기의 bbox를
    가짐), 사실상 칸 안의 거의 모든 도안이 이 배경 경계선에도 동시에 닿아버려 기준을 통과 못 함 --
    카드 케이스뿐 아니라 라쿤 시트 자체도 지나치게 잘게 쪼개지는 새로운 문제가 생김(실측: 두 파일
    모두 20개 넘는 조각으로 과분할).
  - 두 방법 모두 실제 파일 기준으로는 이미 검증/배포된 "카드 + 테두리 장식" 안전장치를 깨뜨리는
    회귀가 실측으로 확인되어, 오늘 안에 안전하게 다듬을 시간이 부족하다고 판단 -- **코드는 전부
    수정 전 상태로 되돌림**(`core/multi_design.py`는 서른두 번째 업데이트 상태 그대로, 변경 없음).
    되돌린 뒤 알고리즘 스모크 테스트(`test_multi_design.py`)와 관련 테스트(세그멘테이션 속도,
    무테 실루엣, 외곽선 폴백, 정밀도) 전부 재실행해 통과 확인 + 두 실제 파일의 실제 칼선 레이어로
    "카드 칸은 그대로 1개 유지, 회귀 없음"을 재확인.

**5) 다음에 시도해볼 만한 방향(오늘은 미착수)**: 배경의 색 경계선처럼 "이미지 폭/높이의 대부분을
가로지르는 가늘고 흐릿한 선"과 "도안 하나의 진짜 외곽선"을 구분하는 기준이 필요해 보임 -- 단순
길이(가로/세로 방향으로 긴 직선인지)만으로는 이 파일의 배경 경계선이 완벽한 직선이 아니라 살짝
구불거려서 못 잡았고, 면적 비율이나 닿는 외곽선 개수만으로는 파일마다 "정상 도안 크기"와 "배경
경계선의 번짐 정도"가 달라 일반화가 안 됐음. 다음엔 배경 경계선 자체를 더 직접적으로(예: 이미지
전체에서 색이 완만하게/서서히 바뀌는 아주 낮은 대비의 넓은 그라데이션 영역을 먼저 찾아 "이 부분은
도안이 아니라 배경"으로 미리 제외하는 방식) 다뤄보는 게 나을 것 같음.

**6) 3번(잠옷 모자 미인식 + 도무송 방향)**: 이번에 받은 8개 파일 중에는 이 증상이 보이는 캡처/파일이
없어서 여전히 재현 못 함 -- 해당 캡처나 파일을 받으면 이어서 진행.

**검증**: `test_multi_design.py` 등 알고리즘 스모크 테스트 전부 재통과 확인(코드를 되돌린 뒤). 실제
파일은 스크래치 폴더에서만 열었고, 확인이 끝난 뒤 `rm -rf`로 즉시 삭제 + `git status --short`와
파일명 검색으로 레포에 실제 파일이나 실제 파일명이 안 들어갔는지 재확인.

**전달**: 코드 변경 없음(원상 복구) + 이 일지.

## 서른네 번째 업데이트

**요청 배경**: 빌드된 실행 파일로 실제 화면에서 도무송/무테를 테스트하던 중 나온 새 피드백들.

**1) "토끼와 딸기" 무테 칼선이 카드 가장자리 밖으로 나가 보임**: 대화로 하나씩 짚어가며 확인한 결과,
이 도안은 배경 무늬가 칸 가장자리까지 끊김 없이 이어지는 "무테" 전용 케이스였고(코드 문서에 이미
있는 실제 예시), 멍푸님이 간격(mm) 칸에 값을 따로 입력하지 않아 기본값 1.2mm만 적용되고 있었음 --
원하시는 최소 2mm보다 작아서 "밖으로 나가 보인" 것으로 보임. 코드 자체는 항상 안쪽으로만 줄이도록
되어 있어(바깥으로 나가는 경로 없음), 간격 칸에 2를 직접 입력해서 확인해보시도록 안내함(이 항목은
아직 최종 확인 답변을 못 받음 -- 다음에 이어서 확인 필요).

**2) 도무송 직사각형 성공 + 남은 문제 2가지 (실제 화면 스크린샷으로 확인)**:
같은 도안(토끼 카드)에 "도무송 > 직사각형"으로 자동 인식을 돌려보니 이번엔 칼선이 정상적으로
나왔음 -- 다만 두 가지를 추가로 지적하심:
  - **모서리가 둥글게 나옴**: `compute_offsets`(core/cutline_core.py)가 도형을 바깥으로 밀 때
    `join_style`(모서리 처리 방식)을 받아서 잘 쓰고 있었는데, 그 바로 다음 "간격 좁으면 합치기"
    단계(buffer(+)/buffer(-) 왕복)는 `join_style`을 안 넘겨줘서 shapely 기본값(둥근 모서리)으로
    다시 깎이고 있었음 -- 실제 사각형으로 재현: 도무송처럼 뾰족해야 할 모서리가 이 단계 때문에
    살짝 둥글어짐. **수정**: 이 합치기 단계에도 같은 `join_style`을 그대로 넘기도록 고침
    (core/cutline_core.py). 완칼(둥근 모서리가 맞는 실루엣 추적)은 그대로 영향 없음(회귀 없음,
    관련 테스트 전부 재통과 확인). 도무송(core/interactive_cutline.py의
    generate_cutline_for_selection)은 이제 `cutline_type.is_domusong`이면 join_style=2(뾰족한
    mitre)를 쓰도록 명시적으로 지정 -- 합성 사각형으로 검증: 도무송 칼선 외곽선이 정확히 4개
    모서리(닫는 점 포함 5개 좌표)로만 이루어짐을 확인(둥근 모서리였다면 각 모서리마다 호를
    근사하는 좌표가 여러 개 더 있었을 것).
  - **안쪽 초록(세이프티) 선이 불필요함**: 도무송을 직접 골라 만들 때는 칼선/블리딩 두 선만
    있으면 충분하다고 확인하심. **수정**: gui/app.py의 "재단 도형 선택"으로 도무송을 직접 만드는
    경로(`_generate_one_item`의 DOMUSONG 분기)에서만 결과의 세이프티 레이어를 화면/내보내기에서
    뺌 -- 최소 간격 계산(enforce_minimum_gap)은 이미 세이프티를 기준으로 다 반영된 뒤라 칼선/
    블리딩 위치에는 전혀 영향 없음, 뺀 건 표시뿐. 마스킹테이프 "롤 전체 테두리" 버튼
    (`_run_add_roll_border`)은 실제 참고 파일에 세이프티까지 포함된 3단 구조가 확인되어 있어
    그쪽은 그대로 둠(다른 요청 범위 아님, 회귀 없음).

**3) "도무송 선택 툴을 작업종류 다음으로 배치하고 설명을 추가해"**: "도무송 세부 옵션"(재단 도형
선택 버튼 + 옵션들) 섹션을 "오프셋 간격"/"유테-무테 간격" 섹션보다 위, "작업 종류" 섹션 바로
다음으로 옮김(gui/app.py) -- 작업 종류를 도무송으로 고르자마자 바로 이어서 도형을 고를 수 있게.
"재단 도형 선택" 버튼 아래에 "실제 칼(금형)이 찍어낼 바깥 모양을 고릅니다 -- 카드/사각 상품은
직사각형, 배지처럼 동그란 상품은 정원형, 캐릭터 실루엣 그대로는 완칼." 설명 문구를 새로 추가.

**검증**: `test_domusong_cell_clip.py`(bounds_px 클리핑), `test_multi_design.py`,
`test_borderless_silhouette.py`, `test_edge_outline_fallback.py`, `test_fidelity.py`,

`test_grid_reconstruction.py`, `test_ai_cutline_reader.py` 전부 재통과 확인. 합성 사각형(알려진
좌표)으로 모서리 좌표 개수를 직접 세어 뾰족한 모서리(정확히 4개 + 닫는 점)를 확인 -- 이건 실제

**미해결**: 1)번 무테 간격 문제는 2mm 직접 입력 테스트 결과를 아직 못 받음. 이전 피드백 목록의

## 서른다섯 번째 업데이트 — 튜토리얼 창 여백, 안내 팝업 글자 강조, "무테+유테 자동 판단" 작업 종류 추가

**요청**: 튜토리얼 창과 "자동 조정 안내" 팝업 캡처와 함께 3가지 피드백을 받음 — 1) 튜토리얼 창 하단
여백이 많아 지저분해 보임, 2) 도무송 적용법이 어렵고 복잡해서 못 하겠음, 3) 작업 종류를 단일 선택이
아니라 2개 이상 선택 가능하게 하고(밑에 "도무송 포함 도안은 도무송 먼저, 나머지는 자동 칼선" 같은
안내 문구도), 글자들이 다 같은 색이라 뭐가 중요한지 모르겠음(알록달록 색은 금지).

**1) 튜토리얼 창 하단 여백**: 원인 확인 -- 튜토리얼 창 높이는 슬라이드마다 다시 계산하면 이전에
확인된 멈춤 버그가 재발할 위험이 있어, 처음 한 번만(가장 긴 설명 문구 기준으로) 고정해두는 방식으로
만들어져 있었음(2026-09-08 결정, 그대로 유지). 그런데 하단 버튼 영역(footer)이 `side="bottom"`으로
창의 진짜 바닥에 고정되어 있어서, 설명이 짧은 슬라이드에서는 버튼 위로 큰 빈 공간이 생기고 있었음.
**수정**: footer의 `side="bottom"`을 빼서 위에서 아래로 순서대로 이어지게 함(gui/app.py,
`_open_tutorial_dialog`) -- 창 높이 계산 자체는 건드리지 않아 멈춤 버그 재발 위험 없음.

**2) 도무송이 어렵다는 피드백**: 이번 업데이트의 3)번 안내 문구 추가와, 이전(서른네 번째) 업데이트의
도무송 도구 재배치로 부분적으로 대응 -- 더 구체적인 개선 요청이 오면 그때 추가 대응.

**3) 작업 종류 다중 선택**: 무엇을 원하시는지 먼저 확인 질문 드렸고, "버튼 한 번에 순서대로 다 처리"를
선택하심(프로그램이 도안마다 알맞은 방식을 자동으로 판단). 실제로 구현 가능한지 검토한 결과, 도무송인지
아닌지는 순수하게 그림만 보고 판단할 수 있는 게 아니라(카드 모양이어도 도무송이 아닐 수 있고, 그
반대도 있음 -- 실제로는 제작 방식에 대한 결정이라 그림만으로는 알 수 없음) 자동 판단에 넣으면 위험하다고
말씀드렸고, "도무송은 따로 선택하게 하자"로 확인하심. **결정**: 자동 판단은 무테/유테 사이에서만
이루어지고, 도무송은 지금처럼 계속 별도로 직접 골라야 함.

  - **구현**: 이미 예전에 한 번 만들어졌다가(2026-08-27) "판단이 틀릴 수 있다"는 이유로 화면에서
    빼뒀던 `core/interactive_cutline.py`의 `generate_cutline_auto` 함수(무테/유테를 각도안마다
    자동으로 판단해주는, 실제 파일 2개로 이미 검증까지 끝난 함수)를 다시 화면에 연결함. 작업 종류
    목록에 "무테+유테 자동 판단"을 새로 추가(gui/app.py) -- 도무송/조각 스티커/마스킹테이프는 전혀
    건드리지 않고, 기존 선택지들과 나란히 놓인 새 항목 하나로 추가한 것뿐이라 회귀 위험 없음. 이
    항목을 고르면: 유테/무테 간격 입력칸이 활성화되고(무테/유테와 동일하게), "자동으로 여러 개
    인식 + 추가" 버튼과 직접 드래그 방식 둘 다에서 사용 가능하며, 도안마다 사각형에 가까운지/배경
    여백이 있는지를 보고 무테 스타일과 유테 스타일 중 알맞은 쪽을 그때그때 골라 칼선을 만듦(어떻게
    판단했는지는 "자동 조정 안내" 팝업에 매번 남김, 예: "자동 감지: 무테 (사각형도 0.91, 기준
    0.85)"). 자동 인식 배치 처리에서 실루엣이 셀 크기의 35% 미만으로 너무 작게 잡히면(예: 몸통
    전체가 아니라 일부만 잡힘) 안전하게 무테(사각형) 컷으로 자동 대체하는 기존 안전장치도 무테/
    유테와 똑같이 적용됨.

  - **"밑에 안내 문구" 요청**: "작업 종류" 섹션에 "한 시트에 도무송 도안이 섞여 있다면: 도무송으로
    그 도안의 칼선을 먼저 만든 뒤, 나머지는 무테/유테로 바꿔 '자동으로 여러 개 인식 + 추가'를
    쓰세요." 안내 문구를 추가함(gui/app.py).

**3) 글자 색 강조 문제**: 확인해보니 기본 글자색(거의 검정)과 보조 글자색(진한 회색)이 실제로 거의

-- 재빌드 후 실제 파일로 사용해보시고 문제 있으면 알려주시면 됨.

## 서른여섯 번째 업데이트 — "도무송, 무테 동시 다중 선택하고 만들어야 해": 도무송으로 만들 도안만 직접 표시하는 "무테/유테+도무송 (직접 표시)" 작업 종류 추가

**요청**: 실제 화면 캡처와 함께 피드백을 받음 -- 튜토리얼 창 하단 여백을 다시 지적하며 "이 부분을
삭제해"(같은 캡처를 재전송하셔서, 재빌드 전 화면일 가능성이 있음 -- 서른다섯 번째 업데이트에서 이미
고쳐 전달함), 그리고 핵심 피드백: "도무송, 무테 동시 다중 선택하고 만들어야 해. 이거 너무
번거러워", "칼선 자동 생성버튼과, 추가 생성 버튼 따로 있어야", "도무송 생성하지, 자동으로 하면 도안
전체에 칼선과 유사한 가이드가 생겨. 토끼는 도무송 작업 안 됐고", "작업 종류 예)무테/유테+도무송으로
칼선 생성됨. 도무송이 포함된 도안은 도무송 칼선 먼저 생성 하기. 로 변경."

**1) 원인 확인(토끼가 도무송 처리 안 된 것)**: 실제 화면(강아지 카드 여러 장 + 둥근 토끼가 꽃 테두리
안에 있는 시트)을 코드로 대조해보니, 지금 "도무송" 작업 종류로 "자동으로 여러 개 인식 + 추가"를
돌리면, 화면에서 고른 재단 도형(예: 직사각형) 하나를 인식된 모든 도안에 무조건 그대로 씌우고
있었음(`gui/app.py`의 `_generate_one_item_for_auto_detect`, DOMUSONG 분기가 개별 도안 종류를
구분하지 않고 항상 같은 `cutline_type`을 씀) -- 카드형 강아지들은 문제 없어 보이지만, 둥근 토끼는
억지로 사각형 틀에 맞춰지면서 이상한 결과가 나온 것. 이 원인을 멍푸님께 먼저 설명드림.

**2) 처리 방식 확인**: "도안마다 다른 모양을 정해야 하는데 어떤 방식이 좋을지" 확인 질문 드림 --
①표시해둔 것만 도무송(추천), ②그림만 보고 자동 판단(위험 감수), ③지금처럼 2단계 유지 중
①(표시해둔 것만 도무송)로 확인하심. 그림만 보고 도무송 여부를 자동 판단하는 건 이미 AUTO_STYLE을
만들 때 한 번 검토했던 것과 같은 이유로 위험함(사각형이어도 실제로는 도무송이 아닐 수 있는, 제작
방식에 대한 결정이라 그림만으로는 알 수 없음) -- 그래서 판단은 항상 사람이 직접 하고, 프로그램은
"표시된 것만 도무송 모양, 나머지는 자동으로 무테/유테"를 실행만 한다.

**3) 구현 -- 새 작업 종류 "무테/유테+도무송 (직접 표시)" (`MIXED_AUTO`)**: 전용 버튼 2개로 나눔
(멍푸님이 요청하신 "자동 생성 버튼과 추가 생성 버튼 따로"에 해당) --

  - **① 도안 자동 인식 (표시하기)**: 시트 안 도안을 전부 찾아(기존 "자동으로 여러 개 인식 + 추가"와
    완전히 같은 감지 로직 재사용 -- 새 알고리즘 없음) 화면에 파란 테두리로 표시만 함. 아직 칼선은
    만들지 않음.
  - **화면에서 직접 표시**: 이 중 도무송으로 만들 도안만 클릭하면 빨간 테두리로 바뀜(다시 클릭하면
    해제). 동일 도안이 반복되는 그룹은 하나만 클릭해도 전체가 함께 표시/해제됨(같은 그림이 하나는
    도무송, 하나는 무테로 다르게 처리될 이유가 없으므로).
  - **② 표시한 대로 칼선 생성**: 빨간색으로 표시한 도안은 재단 도형 선택 + 오프셋 간격(세이프티/칼선/
    블리딩)으로 도무송 칼선을(세이프티 선은 서른네 번째 업데이트와 동일하게 화면에서 뺌), 표시 안 한
    나머지는 "무테+유테 자동 판단"과 완전히 같은 방식(`generate_cutline_auto`, 실루엣이 너무 작게
    잡히면 안전한 사각형으로 자동 대체)으로 칼선을 만들어 한 번에 누적함.

  기존 작업 종류(도무송/무테/유테/무테+유테 자동 판단/조각 스티커/마스킹테이프)의 코드 경로는 전혀
  건드리지 않고 완전히 새로운 조건 분기로만 추가함(`job_type` 자체를 다중 선택 집합으로 바꾸는 건
  2026-09-07에 이미 위험하다고 검토되어 기각된 방식이라, 그 결정을 그대로 따름). "이 영역 추가"(기존
  단일 드래그 생성 버튼)로 이 작업 종류를 시도하면 전용 버튼을 쓰라는 안내 오류가 뜸.

**검증**: 파이썬 문법 검사(`ast.parse`) 통과. 새로 추가한 메서드 8개가 전부 정상적으로 파싱되는 함수로
정의됐는지 확인. `test_domusong_cell_clip.py`, `test_multi_design.py`, `test_borderless_silhouette.py`,
`test_edge_outline_fallback.py`, `test_fidelity.py`, `test_pipeline.py`, `test_repeat_grid.py`,
`test_silhouette_fallback.py`, `test_grid_reconstruction.py`, `test_ai_cutline_reader.py` 전부
재통과(25개, core 로직은 이번에 변경하지 않았으므로 영향 없음이 기대대로 확인됨). `job_type`을
참조하는 모든 분기(sec4/sec5/sec6 활성화, 검증, 생성 경로 등)를 하나하나 다시 대조해 새 작업
종류가 필요한 곳엔 들어갔고 기존 도무송/무테/유테 전용 로직에는 영향이 없는지 확인. 이 분석
환경에는 tkinter가 없어 실제 클릭/캔버스 동작을 직접 눈으로 확인할 수는 없었음 -- 코드 검토와
기존에 이미 실사용으로 검증된 패턴(단일 선택 사각형 그리기, 배경 스레드 처리 등)을 최대한 그대로
재사용하는 방식으로 위험을 낮춤.

**전달**: gui/app.py 수정 + 이 일지 (README.md는 뒤이어 업데이트). `device_commit_files` 전송 후
원격 파일 크기(220932바이트)가 로컬 파일 크기와 정확히 일치함을 확인함.

**남은 것**: exe_빌드.bat로 다시 빌드한 뒤 실제 파일로 꼭 테스트 부탁드림 -- 특히 ①번으로 표시한
도안 개수/위치가 예상과 맞는지, 클릭으로 표시/해제가 잘 되는지, ②번 결과에서 표시한 도안만
정확히 도무송 모양으로 나오는지 확인 필요. 튜토리얼 하단 여백은 이미 서른다섯 번째 업데이트에서
고쳤으니, 재빌드 후에도 여전히 남아있으면 다시 알려주시면 됨.

## 서른일곱 번째 업데이트 — 실제 재빌드 사용 후 3가지 후속 피드백: 튜토리얼 여백/문구 마무리, 도무송→나머지 순서로 생성 분리, 반복 스티커 중복 계산 줄임

**요청**: 서른여섯 번째 업데이트를 재빌드해서 실제로 써보신 화면 캡처와 함께 피드백을 받음. 새
"무테/유테+도무송 (직접 표시)" 기능이 실제로 동작해서 ①번으로 35개 그룹이 표시되고 ②번으로
칼선이 만들어지는 것까지 확인됨(왼쪽 첫 번째 시트는 스티커가 모두 제대로 표시됨). 다만 3가지를
추가로 지적하심 -- (1) "튜토리얼 하단의 공백 모두 삭제, 말이 너무 길어 단순하고 직관적으로 15자
이내로", (2) "도무송은 먼저 선택해서 생성하고, 그다음에 다음 종류 선택하는 방향으로 가고", (3)
"도안에는 똑같은 스티커가 반복 배치 되니까. 한개의 스티커만 칼선 정확하게 생성하고 나머지 도안에
복사해서 붙여넣기 하는게 나을 것 같아. 지금 토큰만 낭비하고 있어".

**1) 튜토리얼 여백 -- 진짜 원인 발견**: 지난번(서른다섯 번째) footer 순서 수정으로도 여백이 안
없어진 진짜 원인을 찾음 -- 창 높이를 정하는 계산(`_open_tutorial_dialog`)의 시작값이
`max_req_h = 400`으로 하드코딩돼 있어서, 캡션을 아무리 짧게 줄여도 실제 필요한 높이가 400보다
작으면 창이 400 밑으로는 절대 안 줄어들고 그 차이만큼 빈 공간이 항상 남았던 것. **수정**: 이
시작값을 250으로 낮춤(250 자체도 디자인 의도가 있는 값이 아니라, 이미지 로드 실패 등 극단적인
경우에 대비한 최소 안전값일 뿐 -- 평소엔 실제로 잰 값이 그대로 쓰임). 동시에 5개 슬라이드 캡션을
전부 15자 안팎의 짧은 한 줄로 통일(예: "도안을 자동으로 인식합니다.\n추가 작업은 마우스 드래그를
통해서\n진행하면 됩니다." -> "도안을 자동으로 인식해요") -- 캡션 길이가 슬라이드마다 들쭉날쭉하지
않게 되어 "가장 긴 캡션 기준" 계산 자체의 편차도 줄어듦. 캡션이 바뀌었으므로 TUTORIAL_VERSION을
4->5로 올려, "다시 보지 않기"를 이미 눌러둔 상태에서도 새 튜토리얼이 한 번은 다시 뜨게 함.

**2) "도무송 먼저, 그다음 나머지" -- 순서대로 진행하는 방식으로 재구성**: 지난 업데이트의 ②버튼
(표시한 도무송 + 나머지 무테/유테를 한 번에 같이 생성)을 ②/③ 두 버튼으로 나눔 -- "② 표시한
도무송 칼선 생성"은 빨간 테두리로 표시한 것만 먼저 생성하고(나머지는 아직 안 건드림), 확인 후
"③ 나머지 무테/유테 칼선 생성"을 누르면 표시 안 한 나머지가 생성됨. 이미 생성을 끝낸 그룹은
`self._mixed_processed` 집합에 기록해둬서, ②③ 어느 순서로 누르든 같은 그룹이 두 번 생성되지
않음. 둘 중 어느 버튼에서 남은 그룹이 다 끝나든, 그 시점에 최종 결과 미리보기로 전환됨(아직 남은
쪽이 있으면 화면의 표시(파란/빨간 테두리)는 그대로 두고 상태 메시지·누적 개수만 갱신 -- 결과
화면으로 넘어가 버리면 아직 안 만든 나머지를 표시할 화면 자체가 사라지기 때문).

**3) 반복 스티커 중복 계산 -- 실제 원인 확인 및 개선**: 코드를 다시 살펴보니, 재단선 격자 한 칸
안의 낱개 요소를 찾는 `detect_sub_element_boxes_px`(Canny 엣지 검출 -- 상대적으로 비용이 큰
연산)를 반복되는 칸이라도 매번 독립적으로 다시 돌리고 있었음(칸끼리 완전히 같은 그림이어도). 이건
(1) 계산이 그만큼 중복되는 문제였고, (2) 독립 실행이라 아주 미세하게 다른 경계 좌표가 나올 수
있어(같은 그림인데 잘라낸 픽셀 경계가 1~2px씩 달라짐) 뒤이은 반복 감지(`group_identical_boxes_px`)
의 내용 비교 임계값을 아슬아슬하게 넘겨 "반복 아님"으로 잘못 갈릴 위험도 있었던 부분(멍푸님이 실제
화면에서 35개 그룹까지 나온 것도 이 영향이 있었을 가능성이 있음, 다만 정확한 원인은 실제 파일을
직접 볼 수 없어 단정할 수는 없음). **수정**: `_expand_grid_cells_into_sub_elements`에서, 칸 안 낱개
요소를 찾기 전에 먼저 칸 자체를 내용으로 묶고(이미 실사용으로 검증된 `group_identical_boxes_px`
재사용 -- 새 알고리즘 아님), 대표 칸 하나에만 실제로 비용이 큰 검출을 실행한 뒤 나머지 반복 칸에는
그 결과를 칸 위치 차이만큼 평행이동해서 그대로 복제함 -- 완전히 같은 좌표 관계이므로 항상 정확히
일치하고, 검출 자체도 칸 개수가 아니라 "서로 다른 칸의 종류" 수만큼만 실행되어 계산량이 줄어듦.

**검증**: 파이썬 문법 검사(`ast.parse`) 통과. 새/변경된 메서드들이 전부 정상적으로 파싱되는 함수로
정의됐는지 확인, 옛 `_on_mixed_generate`가 완전히 제거되고 `_on_mixed_generate_domusong`/
`_on_mixed_generate_rest`/`_run_mixed_generate_subset`로 대체됐는지 확인. `test_domusong_cell_clip.py`,
`test_multi_design.py`, `test_borderless_silhouette.py`, `test_edge_outline_fallback.py`,
`test_fidelity.py`, `test_pipeline.py`, `test_repeat_grid.py`, `test_silhouette_fallback.py`,
`test_grid_reconstruction.py`, `test_ai_cutline_reader.py` 전부 재통과(25개, core 로직은 이번에
변경하지 않음). `job_type`/`mixed_generate` 관련 코드/주석 전체를 다시 grep해 옛 버튼 이름을
가리키는 낡은 문구가 남아있지 않은지 확인하고 전부 새 문구로 정리함.

**전달**: gui/app.py 수정 + 이 일지 (README.md는 뒤이어 업데이트). `device_commit_files` 전송 후
원격 파일 크기(231297바이트)가 로컬 파일 크기와 정확히 일치함을 확인함.

**남은 것**: exe_빌드.bat로 다시 빌드한 뒤 실제 파일로 테스트 부탁드림 -- 특히 (1) 튜토리얼 여백이
이번엔 정말 없어졌는지, (2) ②(도무송)를 누른 뒤 화면이 그대로 유지되면서 ③(나머지) 버튼으로 이어
진행할 수 있는지, (3) 반복되는 스티커가 실제로 그룹 수가 줄어들어 더 빠르게 처리되는지(예: 이전엔

경로를 훨씬 끝까지 추적해서 실제 원인을 구체적으로 찾아내고, 확실하지 않은 부분은 확실하지 않다고
이 일지에 그대로 남긴다.

**(3)+(4) 원인 규명 — 두 문제가 사실 하나의 원인**: `gui/app.py`의
`_expand_grid_cells_into_sub_elements`(격자 칸 안에서 색 경계(Canny)로 낱개 요소를 찾아 칸 하나를

"카드 한 장 + 테두리 장식"엔 잘 걸러지지만, 캐릭터 하나에 자연스럽게 딸린 장식 조각(얼굴/리본/작은
배지 여러 개/하트/달 장식 등)에는 걸러지지 않는다 — 이런 조각들도 색 경계 기준으로는 5개 이상 잡히고

조각들 중 화면에서 표시(클릭)한 것 하나만 도무송으로 만들어지고 나머지 조각은 엉뚱하게 무테/유테로
처리돼 원래 하나였던 토끼 모양이 기형적으로 나뉘어 보이는 것("토끼 칼선 문제")까지 같은 원인으로
설명됨. 이 기능은 이미 2026-09-08(11차)에 카드형 도안에서 한 번 회귀를 냈다가 되돌려졌고, 이번에

**(3)+(4) 수정**: 세 번째로 추측 기준을 또 넣는 대신, 이 확장 기능을 다시 껐다 — 이제

## 마흔일곱 번째 업데이트 — 칼선이 뭉개지고/뚫리고/합쳐지던 문제 원인 확인 및 수정

**조사(합성 좌표로 재현)**: `core/accumulate.py`의 `combine_results`가 시트에 누적된 모든 도안의

연산을 통과해 미묘하게 깎이거나(뭉개짐), 여러 조각이 한 번에 union될 때 구멍이 생길 위험(뚫림)이
있음을 확인. 도안이 촘촘히 배치된 시트일수록 이 영향이 커짐 -- 보고하신 시트들과 정확히 일치.
(다듬기 배율 8배/10배 자체는 별도로 합성 도형으로 비교했을 때 뭉개짐 차이가 거의 없어 원인에서
제외함.)

buffer(+)/buffer(-)하도록 변경 -- 2mm 규칙(최우선 순위 필수 규칙)은 그대로 유지하면서, 무관한
도안은 buffer 자체를 거치지 않아 원본과 완전히 동일하게 보존됨(새 테스트로 확인).

**참고**: 무테 자체의 margin(간격) 계산은 각 도안이 "자기 칸 안쪽으로" 독립적으로 줄어드는
방식이라 이웃과 겹칠 일은 원래 없음 -- 이번에 확인된 증상은 combine_results의 전역 병합 단계가
원인이었음. 재빌드 후에도 간격이 이상하면 어느 부분이 다른지 다시 봐주세요.

**남은 문제**: 같은 시트 아래쪽 빈 칸 2개는 48차 수정 후에도 여전히 칼선이 생겼습니다. 원인을

슬롯이 문제였습니다 -- hole-fill이 그 테두리 안쪽을 캐릭터든 빈 테두리든 구분 없이 꽉 채우기
때문에, 48차의 "얇은 띠 제외" 필터로는 못 걸러졌습니다(테두리 자체는 얇아도 안쪽까지 채워지면
두께가 크다고 나옴). 처음엔 안쪽을 깎아내는(erode) 방식을 시도했으나 합성 테스트로 확인해보니
효과가 없었고(이미 꽉 채워진 덩어리라 거의 안 줄어듦), 최종적으로 "그 덩어리의 원래 색이 배경
색과 같은가"로 판단하는 방식으로 교체했습니다(실제 도안은 배경과 색이 달라야만 애초에 엣지로
잡히므로, 색이 배경과 같으면 빈 테두리로 봄).

**수정**: `cell_has_content_px`뿐 아니라, 실제 재단선 격자가 없는 파일이 쓰는 대체 경로
(`detect_design_bboxes_px`가 공유하는 `_detect_boxes_from_gray`)에도 같은 배경색 비교 필터를
추가했습니다 -- 이 시트가 어느 경로를 타든 같은 문제가 생길 수 있어서입니다. 새 테스트 3개(빈
테두리/실제 캐릭터/대체 경로) + 기존 테스트 전부 통과.

**정직하게**: 이번에도 실제 파일 확인은 재빌드 후에나 가능합니다. 세 번째 재발이었던 만큼, 이걸로도
여전히 빈 칸에 칼선이 생기면 그 칸의 배경이 정확히 어떻게 생겼는지(줄무늬인지, 테두리인지, 완전
단색인지) 확대 캡처로 알려주시면 더 정확히 잡을 수 있을 것 같습니다.

**전달**: core/multi_design.py 수정 + 새 테스트(`test_blank_cell_hollow_frame.py`) + 이 일지.

## 쉰 번째 업데이트 — "스티커마다 칼선 안 됨" 세 번째 재도전(칸 안 낱개 요소 쪼개기)

**요청하신 것**: 강아지 배경 시트에서 패널 하나 안 여러 스티커(강아지 얼굴/사람/식물/하트 등)가 하나로
뭉뚱그려지는 문제 — "2번(어려운 쪽) 진행, 오래 걸리면 그렇다고 알려줘"로 선택하신 작업.

이 기능은 이미 두 번 껐다 켰다 했던 이력이 있습니다(9/8 도입→11차 되돌림: 카드+테두리 장식이 낱개로
오인됨 / 9/10 37차 재도입→38차 재재확인 후 되돌림: 캐릭터 하나에 딸린 장식 조각들이 크기가 제각각이라
안전장치를 통과해버림). 두 번 다 "개수 + 크기"로 구별하려다 실패했습니다.

**이번 시도(기준 자체를 바꿈)**: "실제 배경 틈이 칸 크기 대비 얼마나 되는가"로 다시 판단합니다.
장식 조각(리본/배지/하트/달 등)은 크기와 무관하게 원래 몸체에 거의 맞닿아 있고, 진짜 서로 다른
스티커는 그 사이에 뚜렷한 배경 공간을 의도적으로 두기 때문에, 이 "거리"가 크기/개수보다 더 근본적인
구별 기준이라고 보고 새로 설계했습니다(`core.multi_design.cluster_boxes_by_gap_px` — 47차 때 칼선
간격 처리에 썼던 union-find 묶기와 같은 원리를 bbox 거리에 적용).

새 함수 `split_cell_into_sub_elements_px`가 이 판단을 전담하고, `gui.app._expand_grid_cells_into_sub_elements`는 칸마다 이걸 호출해 이어붙이기만 합니다. 합성 테스트로 확인한 것(`test_split_cell_by_gap_clustering.py`, 4개 케이스):
- 카드 한 장 + 테두리 장식 8개(11차 실패 패턴 재현) → 1개로 유지 (통과)
- 캐릭터 하나 + 장식 조각 5개, 크기 제각각(38차 실패 패턴 재현) → 1개로 유지 (통과)
- 서로 뚜렷이 떨어진 스티커 4개(강아지/사람/식물/하트 자리) → 4개로 쪼개짐 (통과)
- 장식 없는 캐릭터 하나뿐인 기본 케이스 → 1개로 유지 (통과)

**정직하게**: 위 4가지는 전부 제가 직접 합성한 이미지로만 검증한 것이라 로직/코드 수준으로만 확인된
상태입니다. 클러스터링 기준값(칸의 짧은 변의 8%)도 합성 이미지로 고른 값이라, 실제 강아지 시트에서
정확히 4개(강아지 얼굴/사람/식물/하트)로 나뉘는지는 재빌드 후 직접 확인이 필요합니다. 이번에도 실패
패턴이 재현되면(장식이 낱개로 쪼개지거나, 반대로 여전히 하나로 뭉침) 어느 쪽으로 잘못됐는지와 대략적인
간격 느낌(장식이 몸체에 거의 붙어 있는지, 스티커들 사이 간격이 넉넉한지)을 알려주시면 기준값을
조정하겠습니다.

**전달**: core/multi_design.py, gui/app.py 수정 + 새 테스트(`test_split_cell_by_gap_clustering.py`) +
기존 테스트 갱신(`test_sub_element_detection.py`) + 이 일지.
