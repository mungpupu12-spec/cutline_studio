# 2026-08-25 개발 일지

## 오늘 목표

"칼선 형태를 최대한 도안 이미지에 가깝게" — 실제로는 두 가지 문제였다:
1. 곡선/대각선 구간에서 오프셋 선이 미묘하게 꺾이거나 튀는 지점이 생김 (픽셀 격자 기반 컨투어 추출의 한계).
2. 반투명(안티에일리어싱) 가장자리를 가진 도안에서, 칼선이 실제 눈에 보이는 도안 경계보다 살짝 더 크게 그려지는 경향.

## 원인 분석

- 기존 파이프라인은 원본 해상도 그대로 이진화(투명 여부 판정) → OpenCV 컨투어 추출 → Douglas-Peucker 단순화(허용오차 1.5px) → Shapely 오프셋 순서였다.
- 문제 1의 원인: 픽셀 격자 위에서 추출한 컨투어는 태생적으로 계단 모양이고, 이후 단순화는 그 계단을 "적당히 완만한 직선들"로 뭉뚱그릴 뿐 실제 곡률을 복원하지 못한다 — 특히 곡선이 급하게 꺾이는 지점에서 계단의 흔적이 오프셋 결과에 남았다.
- 문제 2의 원인: 알파 임계값을 20(매우 낮음)으로 잡고 있어서, 반투명한 안티에일리어싱 테두리 픽셀까지 전부 "도안 안쪽"으로 잡아버렸다 — 그만큼 실루콘이 실제보다 커진 채로 모든 오프셋 계산의 기준이 됨.

## 수정 내용 (`core/cutline_core.py`)

1. **서브픽셀 컨투어 추출**: 원본 해상도에서 노이즈 제거(모폴로지 open/close)까지 마친 이진 마스크를 4배 업샘플링(선형 보간) → 가우시안 블러로 계단의 모서리를 완만하게 함 → 중간값(127)에서 재이진화 → 그 확대된 해상도에서 컨투어 추출 → 좌표를 다시 1/4로 축소. 이렇게 하면 곡선/대각선 구간이 원본 픽셀 격자보다 훨씬 매끄럽게 추적된다.
2. **임계값을 중간값(127) 기준으로 변경**: 투명 PNG는 알파 20→127로, 흰 배경 플랫 이미지는 고정값 245 대신 Otsu 자동 임계값으로 — 두 경우 모두 "실제 눈에 보이는 경계"에 최대한 가깝게 이진화 경계를 맞췄다.
3. 단순화 허용오차를 1.5px → 0.6px로 낮춤 (서브픽셀 컨투어라 더 촘촘히 따라가도 결과가 지저분해지지 않음).

## 검증

- 합성 원(anti-aliased, 반경 110px @300dpi) 기준: 칼선이 이론상 정확한 오프셋 원과 벌어지는 정도가 평균 0.47px → 0.24px, 최대 1.04px → 0.52px로 절반 가까이 줄었고, 기존 파이프라인이 갖고 있던 "항상 +0.37px만큼 바깥으로 치우치는" 체계적 오차도 대부분 사라졌다 (`test_fidelity.py`).
- **정직하게 밝혀둘 것**: 안티에일리어싱이 전혀 없는(하드 엣지) 합성 이미지로 같은 테스트를 하면 이 개선은 오히려 아무 도움이 안 됐다 — 애초에 복원할 서브픽셀 정보 자체가 없기 때문. 즉 이 개선의 실질적 효과는 "매끄러운 안티에일리어싱 경계를 가진 실제 아트웍"에서 나온다.
- 승인받은 실제 납품용 캐릭터 PNG(투명 배경, 3500×3500) 한 장으로 재확인: 체리 꼭지처럼 가늘고 굽은 부분에서 기존 결과는 오프셋 선이 살짝 꺾이는 지점이 눈에 보였는데, 새 결과는 그 구간이 매끈하게 이어진다. 얇은 부분 위험 감지도 그대로 정상 동작 확인(해당 파일 자체나 파일명은 저장소에 포함하지 않음).
- 기존 회귀 테스트(`test_pipeline.py`, `test_risk.py`, `test_vector.py`) 전부 이상 없음.

## 성능 참고

- 3500×3500 실제 파일 기준 도안 추출에 약 2.3초 소요 (기존 0.16초보다 느려짐 — 4배 업샘플링 비용). 데스크톱 앱에서 "생성" 버튼 누르고 몇 초 기다리는 정도로, 아직은 허용 범위로 판단. 이후 이미지가 훨씬 커지면 업샘플 배율을 자동으로 낮추는 것도 고려할 것.

## 추가 업데이트 — 최소 안전 간격 강제 (같은 날)

**요청 배경**: 칼선이 도안에 너무 가깝게 잡히면, 실제 인쇄/커팅 과정에서 미세하게 밀리는 것만으로도
칼선이 도안을 잘라먹을 수 있다는 실무 피드백. 오프셋 값을 세이프티/칼선/블리딩 각각 자유롭게 입력할 수
있게 해뒀던 게, 값을 너무 작게(또는 0으로) 넣어도 그대로 통과되는 게 문제였음.

**수정**: `core/cutline_core.py`에 `OffsetSpec.enforce_minimum_gap()` 추가.
- 세이프티/칼선/블리딩 중 도안에서 가장 가까운 선이 1mm보다 가까우면, **세 값 모두를 같은 만큼
  바깥으로 밀어서** 가장 가까운 선이 정확히 1mm가 되도록 자동 조정.
- 예: 0.3 / 0.8 / 1.5mm로 입력 → 1.0 / 1.5 / 2.2mm로 조정 (세 선 사이의 간격 0.5mm, 0.7mm는 그대로
  유지 — 값을 각각 따로 1mm로 올려버리면 세이프티랑 칼선이 같은 위치에 겹쳐버리는 문제가 생겨서,
  전체를 통째로 미는 방식을 택함).
- 이미 1mm 이상이면 아무 것도 안 바뀜 (기본값 1.0/2.0/3.0mm는 원래도 안전).
- `generate_cutlines()`가 항상 이 검사를 거치도록 연결 — GUI든 스크립트든 우회 불가능.
- GUI(`gui/app.py`)는 조정이 일어나면 스핀박스 값도 실제 사용된 값으로 다시 맞추고, 상태창 + 팝업으로
  "왜 바뀌었는지" 바로 알려줌 — 조용히 값만 바뀌는 일은 없도록 함.

**검증**: 기존 회귀 테스트(`test_pipeline.py`, `test_risk.py`, `test_vector.py`) 전부 이상 없음 — 기본값
1.0/2.0/3.0mm는 이미 안전해서 결과가 그대로임. 별도로 0.3/0.8/1.5mm, 0/0/0mm 입력 케이스를 직접 확인해
의도대로 동작하는 것 확인.

## 세 번째 업데이트 — 시트 전체(씰스티커) 작업 + 가이드 우선 체크 (같은 날)

**요청 배경**: 도안 한 장씩만 칼선을 따는 게 아니라, 실제로는 씰스티커 한 시트에 여러 도안을 배치해서
한 번에 작업한다. 그리고 인쇄소/작업 가이드(용지 종류별로 실제 슬롯 크기, 재단/칼선 경계가 정해져
있음)를 먼저 확인하고 그 기준에 맞게 이미지를 배치·작업해야 한다는 실무 피드백.

**승인받은 실제 가이드 파일 확인** (`성함 , 파일명 , 용지종류 , 코팅종류 , 제작매수 - 씰스티커 가이드
(cs6).ai`, PDF 호환이라 PyMuPDF로 직접 열어 구조 분석): 페이지 전체에 재단가이드(파란색, 시트 맨
바깥쪽)와 칼선가이드(자주색, 재단선보다 살짝 안쪽) 두 겹의 시트 경계선이 있고, 그 안에 12개의 개별
도안 슬롯(3열×4행, 슬롯당 약 46.2×67.5mm, 역시 자주색 사각형)이 그려져 있으며, "이 선을 넘어가지
않도록 작업해주세요"라는 안내 문구가 텍스트로 박혀 있음.

**추가한 모듈**:
- `core/guide.py` — 가이드 파일(.ai/PDF 호환)을 열어 시트 전체 크기, 재단/칼선 경계선, 개별 슬롯
  칸들을 자동으로 읽어내는 `load_guide_from_ai()`. 특정 파일의 숫자를 하드코딩한 게 아니라 "페이지의
  30% 이상 크기 사각형 = 시트 경계", "비슷한 크기로 여러 번 반복되는 작은 사각형 그룹 = 슬롯 격자"
  같은 일반적인 규칙으로 판별 — 다른 용지 종류의 가이드 파일이 생겨도 그대로 쓸 수 있게 했다.
  (첫 시도에서는 가이드 안내 문구("칼선가이드...") 자체가 자주색 글자 획(글리프)이라 이게 작은
  사각형 여러 개로 오인식돼서 슬롯으로 잘못 잡혔음 — 최소 슬롯 크기(15mm) 기준과 그룹 내 크기
  일관성(분산)을 같이 봐서 진짜 슬롯 격자만 골라내도록 수정.)
- `core/sheet_layout.py` — 여러 도안 이미지를 가이드의 슬롯 칸에 순서대로(왼쪽→오른쪽, 위→아래)
  배치해서 시트 전체 합성 이미지를 만드는 `place_designs_into_sheet()`. 중요한 원칙: **도안을 슬롯에
  맞춰 몰래 축소하지 않는다.** 기본값은 도안의 원래 크기(작업 DPI 기준) 그대로 슬롯 중앙(투명 여백이
  아니라 실제 그림이 있는 부분 기준)에 놓고, 슬롯 경계를 넘으면 "넘어간다"고 그대로 알려준다. 실제
  목표 크기(mm)를 알고 있으면 `target_sizes_mm`로 명시적으로 지정해서 그 크기에 맞춰 배치할 수 있음.

**실제 검증**: 승인받은 실제 캐릭터 PNG 4장(디저트 마테 폴더)으로 두 가지 다 확인함.
1. 원본 그대로 배치 → 4장 다 "슬롯보다 훨씬 크다"는 위반이 정확히 잡힘 (원본 파일들이 최종 인쇄
   크기보다 훨씬 큰 해상도로 작업된 마스터 원본이라, 이 결과가 오히려 정직하고 맞는 동작. 조용히
   축소해서 "됐다"고 하지 않음).
2. 슬롯 크기의 85%로 명시적으로 맞춰 배치 → 위반 없음, 시트 전체를 하나의 이미지로 합쳐서
   `generate_cutlines()`에 넣었더니 4개 도안이 겹치지 않고 각각 개별 영역으로 정확히 인식되고, 각각에
   세이프티/칼선/블리딩이 정상적으로 생성됨. (이 두 검증에 쓴 실제 캐릭터 이미지·합성 결과는 저장소에
   넣지 않음 — 대화창으로만 확인.)

**공개 저장소용 재현 버전**: 실제 가이드 파일과 캐릭터 이미지는 커밋하지 않으므로, 같은 구조(큰 재단/
칼선 사각형 + 반복되는 작은 슬롯 사각형)를 가진 가짜 가이드(`samples/make_guide_demo.py` →
`samples/guide_demo.pdf`)와 합성 캐릭터 4개(`samples/make_sheet_chars.py`)를 새로 만들어
`test_sheet_demo.py`로 똑같은 흐름(가이드 로드 → 위반 감지 확인 → 슬롯에 맞춰 배치 → 시트 전체 칼선
생성 → 검증)을 아무나 클론해서 그대로 재현해볼 수 있게 함.

**의존성 추가**: `requirements.txt`에 `PyMuPDF` 추가 (.ai/PDF 가이드 파일을 읽기 위해 필요).

**다음에 할 일**: 가이드에서 읽은 슬롯 정보를 GUI에도 연결해서, 파일 선택 대신 "가이드 파일 + 도안
여러 장"을 한 번에 넣고 시트 전체 미리보기를 볼 수 있게 만드는 것 (지금은 스크립트 레벨까지만 구현).

## 네 번째 업데이트 — 실제 완성 납품 파일 피드백 반영 (같은 날)

**요청 배경**: 실제로 완성해서 납품한 파일 스크린샷을 보내며 6가지 피드백을 줬다:
1. 이미지가 가이드 안쪽에 들어갈 크기로 자동 지정되지 않음.
2. 칼선이 여전히 너무 가까움 — 최소 간격을 1mm에서 2mm로.
3. 이미 가이드 안에 정렬된 이미지는 크기·화소 변동 없이, 그 위에 칼선만 담은 새 레이어를 만들 것.
4. **내가 준 파일 외의 이미지 생성/학습은 금지** — 합성 테스트 데이터를 더 이상 만들지 말 것.
5. 첨부한 실제 예시를 제대로 학습할 것.
6. 실제 파일(`1조수희_5_유포지_벨벳소프트(cs6).ai`)의 사본을 만들어서, 그 안에 이미 배치된 이미지 위에
   칼선을 생성하고, 간격/밀림으로 인한 파본 방지 기능을 그 실제 파일로 같이 테스트·개발할 것.

**이 지침에 따라 오늘부터 새로운 검증/테스트용 합성 데이터(가짜 캐릭터, 가짜 가이드 등)는 더 이상
만들지 않는다.** (이전에 만든 `samples/guide_demo.pdf`, `samples/sheet_char_*.png`, `test_sheet_demo.py`는
"클론한 사람이 그대로 재현해볼 수 있는 공개 저장소 데모"라는 별개 목적으로 이미 커밋되어 있어 그대로
남겨두되, 앞으로의 실제 개발/검증은 전부 작가님이 주신 실제 파일로만 진행한다.)

**실제 파일 구조 확인**: `1조수희_5_유포지_벨벳소프트(cs6).ai`를 PyMuPDF로 직접 열어 분석.
- 레이어(OCG) 6개, 스크린샷과 정확히 일치: `가이드라인`, `개별재단 레이어`, `칼선레이어`, `인쇄레이어`,
  `SA regmark...`, `SA info...`.
- `인쇄레이어`는 이미지 1장(CMYK, 4495×3074px, 300dpi 상당)으로 완전히 플랫된 상태 — 개별 캐릭터가
  레이어로 분리돼 있지 않고 하나의 인쇄용 래스터로 합쳐져 있음.
- `칼선레이어`에는 실제 손으로 딴 칼선 패스가 106개 있고, 그중 105개는 진짜 베지어 곡선으로 캐릭터
  실루엣을 따라 그린 것, 1개는 단순 사각형(토끼 칸 — 이 칸만 개별 실루엣이 아니라 사각 다이컷으로
  작업했다는 뜻).
- `개별재단 레이어`에는 반복 단위(동일한 씬이 6~7번 찍힌 것) 사이를 나누는 격자 구분선 10개가 있음
  (실루엣 칼선이 아니라 시트를 몇 개의 큰 조각으로 나누는 재단선).

**수정 1 — 최소 간격 1mm → 2mm** (`core/cutline_core.py`): `MIN_GAP_MM = 2.0`으로 상향. 기존
`enforce_minimum_gap()` 로직(세 선을 통째로 밀어서 상대 간격 유지)은 그대로 재사용, 기본값만 바뀜.

**수정 2 — 가이드 슬롯 자동 맞춤 기본값으로 전환** (`core/sheet_layout.py`): `place_designs_into_sheet()`에
`auto_fit=True`(기본), `fit_margin_mm` 파라미터 추가. 이전에는 `target_sizes_mm`를 명시하지 않으면
원본 해상도 그대로 놓고 슬롯보다 크면 "위반"이라고만 알렸는데, 실제로는 이게 오히려 불편했다 — 대부분의
마스터 원본은 슬롯보다 훨씬 크게 작업되고, 실제로 원하는 건 "슬롯에 맞춰 넣어달라"는 것. 이제 기본
동작이 슬롯 크기(빼기 `fit_margin_mm` 여백)에 맞춰 비율 유지하며 자동 축소(단, 이미 슬롯보다 작은
도안을 억지로 확대하지는 않음 — 화질 저하 방지). `target_sizes_mm`를 명시하면 여전히 그 값이 최우선.

**수정 3 — 레이어 보존형 칼선 추가** (`core/ai_layer_export.py`, 신규): 기존 .ai(PDF 호환) 파일을 열어
새 OCG 레이어 하나(또는 safety/cut/bleed 각각 하나씩)를 추가하고, 그 레이어 안에만 칼선 벡터 패스를
그려 넣는 `add_cutline_layer_to_ai()`. 기존 이미지 xref나 다른 레이어는 전혀 건드리지 않음 — PyMuPDF로
새 콘텐츠만 얹는 방식이라, 저장 후에도 원본 이미지의 바이트가 100% 동일함을 직접 확인했다(아래 검증
참고). 레이어 이름은 `칼선레이어_자동생성`으로, 작가님이 손으로 그린 `칼선레이어`와 절대 헷갈리지 않게
구분했고, 선 색도 자주색이 아니라 파란색으로 다르게 넣었다.

**실제 파일로 검증** (지침 4, 6 반영 — 전부 실제 파일, 합성 데이터 없음):
1. `1조수희_5_유포지_벨벳소프트(cs6).ai`를 사본으로 복사(`..._사본_자동칼선테스트.ai`), 원본은 절대
   건드리지 않음.
2. 사본 안에서, 이미 가이드에 맞춰 배치된 실제 이미지 중 "토끼" 칸(테두리 프레임 + 토끼 캐릭터, 배경이
   거의 균일한 연보라색이라 기존 알파/오츠 임계값 파이프라인이 그대로 통함)을 잘라내 내 도구의
   `generate_cutlines()`를 그대로 실행 → 프레임 장식 4개 + 덩굴 + 토끼 몸통 등 13개의 개별 실루엣을
   자동으로 찾아내고, 세이프티 1mm/칼선 2mm/블리딩 3mm로 넣었더니 최소 간격(2mm) 미달로 자동 조정돼
   실제로 세이프티 2mm/칼선 3mm/블리딩 4mm가 적용됨 — 2mm 최소 간격 기능이 실제 파일에서 정확히
   의도대로 작동하는 것 확인.
3. `add_cutline_layer_to_ai()`로 사본에 실루엣/safety/cut/bleed 4개 레이어를 추가 저장한 뒤 다시 열어서:
   기존 이미지(xref 16) 바이트가 저장 전후 100% 동일(`doc.extract_image()` 비교), 기존 레이어 6개가
   그대로(`get_ocgs()` 비교), 기존 칼선레이어의 106개 패스도 그대로 남아있음을 코드로 직접 대조해 확인.
   지침 3("크기·화소 변동 없이 레이어를 생성해 그 안에 칼선을 만들어")을 정확히 충족.
4. **정직하게 밝혀둘 것 — 흥미로운 실제 비교**: 이 토끼 칸의 기존 손그린 칼선은 캐릭터 실루엣을 따라간
   게 아니라 칸 전체를 감싸는 단순 사각형 다이컷이었다. 실제 도안 잉크(배경이 아닌 픽셀)까지의
   최소 여백을 직접 측정해보니 약 3.56mm로, 새 최소 기준(2mm)보다 넉넉해서 이 칸 자체는 안전한
   상태였다. 즉 이번 실제 파일에서는 "위험한 파본 사례"를 찾은 게 아니라, 내 도구가 자동 생성하는
   촘촘한 실루엣 칼선과 작가님이 실제로 선택한 단순 사각 다이컷이 서로 다른 접근이라는 걸 확인한
   것 — 어느 쪽이 맞다/틀리다가 아니라 제품 특성에 따라 다르게 쓰일 수 있는 선택지임을 알게 됨.
   비교 이미지는 대화창으로 전달(실제 파일 파생 이미지라 저장소에는 넣지 않음).
5. **한계도 정직하게**: 씬 전체가 반복되는 큰 타일(문/보름달/여러 캐릭터가 한 배경 위에 다 그려진 것)은
   배경 자체가 균일하지 않아서(하늘 그라데이션, 나무, 꽃잎이 서로 겹침) 지금의 알파/오츠 기반 실루엣
   추출로는 캐릭터 하나하나를 자동으로 분리해낼 수 없다 — 이건 이번에 다룬 "투명 배경 또는 거의 균일한
   배경" 케이스와는 다른, 색상 기반 객체 분리(세그멘테이션)가 필요한 더 어려운 문제. 실무적으로는 이런
   복잡한 씬은 최종 플랫 이전(캐릭터가 아직 각자 레이어/투명 배경으로 분리돼 있는 단계)에 이 도구를
   돌리는 게 지금 파이프라인에 맞는 방법이라고 판단됨 — 다음에 이런 파일을 검증할 기회가 있으면 그
   단계의 원본이 있는지 확인해볼 것.

**다음 아이디어 (구현 전)**: 토끼 칸 검증 중에, 새 칼선을 "생성"하는 것 말고 이미 그려진 칼선(수작업
포함)이 실제 잉크와 얼마나 떨어져 있는지 역산해서 2mm 미만인 구간을 자동으로 잡아주는 "기존 칼선
간격 검사" 기능이 있으면 실무에 바로 쓸모 있겠다는 걸 확인했다. 다음 후보 기능으로 기록.

**전달**: 사본 파일(`..._사본_자동칼선테스트.ai`, 원본 위치에 새 파일로)과 비교 이미지는 실제 작업
파일에서 나온 결과라 GitHub 공개 저장소에는 올리지 않고, 작가님 컴퓨터의 원본 폴더와 대화창으로만
전달함. 공개 저장소에는 이번 항목의 코드(`core/cutline_core.py`의 2mm 상향, `core/sheet_layout.py`의
자동 맞춤 기본값, `core/ai_layer_export.py` 신규 모듈)만 커밋.

## 다섯 번째 업데이트 — 칼선 종류 구분, 유색 배경 자동 분리, 반복 배치, 근접 병합 (같은 날)

**요청 배경**: 네 번째 업데이트에서 "토끼 칸이 단순 사각형이라 아쉽다"는 식으로 정리했었는데, 이건
내가 잘못 짚은 것이었다 — 실제로는 **직사각형이 도무송(Thomson-die) 칼선이라는, 실무에서 가장 많이
쓰는 방식**이었다. 정정 피드백을 받고 알게 된 것:

- 칼선은 크게 두 종류다. **도무송**은 정해진 도형(정원형/타원형/정사각형/직사각형)으로 만드는 물리적
  다이 칼선 — 도구를 새로 만들 필요 없이 표준 규격으로 빠르게 자를 수 있어서 실무에서 가장 많이 쓰임.
  **완칼**은 도안 하나의 실루엣을 그대로 따라가는 칼선 — 캐릭터 모양 자체가 상품인 경우에 씀.
- 실제 작업 흐름은: 칼선 작업할 이미지 영역을 먼저 드래그로 지정 → 원하는 칼선 종류(버튼)를 선택해서
  생성.
- **일반적인 씰스티커 칼선은 거의 다 유색 배경 위에서 진행된다** — 이게 실제로 작업 시간이 오래 걸리는
  핵심 이유이고, 이 프로그램을 만드는 이유이기도 하다는 걸 다시 강조받음. 지금까지 내가 "완칼은 투명/
  거의 균일한 배경에서만 된다"고 한계로 적어뒀던 게, 사실은 **이걸 풀어내는 게 이 프로젝트의 핵심
  과제**라는 뜻이었다.
- 다만 실제로 많이 쓰이는 패턴(같은 이미지가 시트에 여러 번 반복)에서는, 반복마다 새로 유색 배경을
  분리하지 않고 **한 개만 정확히 만들어서 나머지는 복사·재배치**하면 난이도가 크게 낮아질 거라는 실용적
  조언을 받음.
- 색상 자체는 전혀 신경 쓸 필요 없음 — 만드는 건 오직 "선"(칼선)이기 때문.
- **앞으로는 실제 자료 파일의 도안으로만 학습/개발**(네 번째 업데이트에서 이미 확정된 방침, 이번에도
  재확인).

**추가한 모듈**:

1. `core/cutline_types.py` — `CutlineType` enum(정원형/타원형/정사각형/직사각형/완칼)과
   `fit_domusong_shape()`/`build_cutline_design()`. 도무송 4종은 전부 "도안 내용물의 bbox를 딱 담는
   기본 도형"을 만드는 것뿐이라, 그 뒤(세이프티/칼선/블리딩 오프셋, 최소 간격 확보)는 완칼과 완전히
   같은 `compute_offsets()`를 그대로 재사용함 — 새 파이프라인을 따로 만들 필요가 없었음.
2. `core/segmentation.py` — **유색/복잡한 배경에서 도안 하나를 분리하는 핵심 모듈**. OpenCV의
   GrabCut(대충 그린 사각형만 주면 안쪽/바깥쪽 색 분포를 반복 추정해서 전경을 골라내는 알고리즘)을
   사용. 작가가 드래그한 박스는 정확할 필요 없음 — 느슨해도 GrabCut이 알아서 다듬음. 추출한 마스크는
   기존 서브픽셀 업샘플링 파이프라인을 그대로 통과시켜서, 어떤 경로로 들어온 도안이든 동일한 정밀도를
   갖게 함.
3. `core/interactive_cutline.py` — 선택 영역 + 칼선 종류 + 오프셋을 하나로 묶는 진입점
   (`generate_cutline_for_selection()`). GUI가 호출하는 곳.
4. `core/repeat_grid.py` — 이미 만든 칼선 하나를 여러 좌표(반복 위치)로 그대로 복사·이동
   (`replicate_by_offsets()`, `grid_offsets_from_origins()`). 각 위치마다 다시 분리를 시도하지 않으므로
   반복본마다 미세하게 다른 결과가 나오는 걸 원천 차단.
5. `core/cutline_core.py`의 `compute_offsets()`에 `merge_gap_mm` 파라미터 추가(기본값 = `MIN_GAP_MM`,
   즉 2mm) — 버퍼로 오프셋을 만든 뒤 "바깥으로 부풀렸다 다시 안으로 줄이는" 표준 모폴로지 클로징
   기법으로, 서로 다른 요소의 선이 2mm 이내로 가까우면 하나로 합침. 도안 자체가 겹치거나 닿을 때만
   합쳐지던 기존 동작보다 한 단계 더 나아간 것.
6. `gui/app.py` — 오른쪽 미리보기를 `Label`에서 `Canvas`로 바꿔서 이미지 위에 마우스 드래그로 영역을
   선택할 수 있게 함, 왼쪽에 칼선 종류 라디오 버튼 5개 + "유색 배경 자동 분리(GrabCut)" 체크박스 추가,
   "선택 영역 지우기"/"원본 다시 보기" 버튼 추가. 선택 영역이 있으면 `interactive_cutline`을, 없으면
   기존 전체 이미지 방식을 그대로 사용 — 기존 사용자에게는 아무것도 안 바뀜.

**실제 파일로 검증** (지침대로 전부 실제 파일, 합성 데이터 없음 — 오늘 이미 사본으로 검증에 써도 된다고
확인된 `1조수희_5_유포지_벨벳소프트(cs6).ai`의 인쇄레이어 래스터 사용):

1. **도무송 4종 vs 완칼**: 같은 실제 토끼 도안에 다섯 가지 칼선을 모두 만들어봄 — 완칼은 몸통만 딱
   따라가고, 타원형은 실제 그 칸의 장식 프레임과 자연스럽게 어울리는 모양이 나오고, 정사각형/직사각형은
   세로로 긴 도안이라 좌우로 여유가 남는 것까지 눈으로 직접 확인. (`output/type_demo_grid.png`, 실제
   도안이 나온 이미지라 저장소 미포함, 대화창으로만 전달)
2. **유색/복잡한 배경에서 GrabCut 분리 — 실제 손그린 선과 직접 대조**: 씬 전체가 반복되는 타일 하나 안의
   강아지 캐릭터(하늘 그라데이션 배경, 옆에 다른 캐릭터들과 맞닿아 있음)를 놓고, 실제 손그린 칼선
   rect를 18~20% 느슨하게 부풀린 "대충 드래그"를 흉내내서 GrabCut에 넣음 → 결과 실루엣과 실제 손그린
   선의 IoU(겹치는 비율) **0.80**. 시각적으로도 강아지의 곱슬머리 스캘럽, 들어올린 앞발 모양까지 꽤
   잘 따라감(`output/grabcut_vs_real_v1.png`). **정직하게 밝혀둘 것**: 내 결과가 실제 선보다 전체적으로
   살짝 바깥쪽으로 크게 나오는 체계적인 경향이 있음(아마 안티에일리어싱 경계 색이 GrabCut 전경 쪽으로
   분류되는 것으로 추정). 마스크를 깎아내는(erosion) 실험을 해봤는데 침식 정도에 따라 결과가 불안정하게
   튀는 문제가 있어(연결된 털 뭉치가 끊기며 컨투어 계층 구조가 꼬이는 것으로 추정) 아직 완전히 해결하지
   못함 — README 로드맵에 다음 후보로 기록.
3. **반복 배치 검증**: 같은 강아지 캐릭터가 실제로 2열×3행(6곳)에 반복되는 걸 실제 파일의 "개별재단
   레이어" 격자선으로 확인한 뒤, 1번에서 분리한 실루엣을 나머지 5곳으로 좌표만 이동해서 복사 →

4. **근접 병합 검증**: 토끼 도안(장식 요소 13개)에 세이프티 오프셋을 적용했을 때, 병합 없이는 8개의

## 여섯 번째 업데이트 — 칼선은 이미지 경계를 넘으면 안 됨, 결과물은 선 하나 (같은 날)

**요청 배경**: 다섯 번째 업데이트에서 보여준 도무송 데모(정원형/정사각형)가 실제로는 **잘려 나간
이미지 경계 밖으로 칼선이 삐져나온 상태**였다 — 대충 자른 테스트용 크롭 이미지를 "이미지 전체"로
취급했더니, 원/정사각형 도형이 그 크롭의 가장자리를 넘어가버린 것. 지적받은 내용:

1. **모든 칼선은 이미지(실제 인쇄되는 캔버스) 안에서만 그려져야 한다** — 물리적으로 존재하지 않는
   잉크 바깥을 다이가 자를 수는 없으니 당연한 제약인데, 테스트 크롭이 잘못돼서 이 제약이 깨진 채로

2. **토끼 칸을 "도무송 사각형이라 문제 없다"고 정리한 것도 틀렸다** — 정확히 뭐가 틀렸는지는 다음
   피드백에서 더 다뤄야 하지만, 적어도 "칼선이 이미지 밖으로 나가면 안 된다"는 원칙을 무시하고
   내린 결론이었다는 점에서 정정 대상.
3. 새로 첨부한 실제 파일(`2조수희_5_유포지_유광코팅(cs6).ai`) 스크린샷 3장(인쇄+칼선 레이어 함께 /
   인쇄레이어만 / 칼선레이어만)이 **"칼선 작업의 기본 원리, 그리고 그게 전부"** — 즉 복잡하게 여러
   겹을 만드는 게 아니라, **도안 하나에 외곽선 하나**를 그 이미지의 실제 옵션(모양)에 맞춰 만드는
   것뿐이라는 걸 다시 명확히 함.
4. 앞으로는 이 파일(`2조수희...`)로 작업.

**수정 내용**:

1. **`core/cutline_core.py`의 `compute_offsets()`에 `clip_bounds` 파라미터 추가.** 세이프티/칼선/

## 일곱 번째 업데이트 — 이미지 종류(선화/무테) 옵션, 토끼 칼선 다시 이해 (같은 날)

**요청 배경**: 여섯 번째 업데이트에서 "토끼는 사각형인데 문제"라고 정리했던 게 방향 자체가 틀렸다는
정정을 받음. 실제로는:

- **토끼 = 무테 도무송 사각형** — 이미 이미지가 셀 전체를 채우고 있어서 캐릭터 내용물을 분석할 필요가
  전혀 없고, 그냥 **이미지(셀) 안쪽으로 사각형 칼선 하나**를 넣으면 끝나는, 실제로 가장 많이 쓰는
  단순한 작업이었다. 지난 업데이트에서 "캐릭터 bbox에 여백을 준 사각형"을 계산했던 게 애초에 잘못된
  기준(캐릭터 내용물)으로 사각형을 만든 것 — 기준은 캐릭터가 아니라 **이미지/셀의 경계 그 자체**여야
  했다.
- 이미지는 실무적으로 두 종류로 나뉜다:
  1. **선화** — 유색 배경 위에 캐릭터가 그려진 경우(반복 타일의 강아지/곰 장면들). 캐릭터 실루엣을
     그대로 따라가되(완칼), 배경에 색이 있으니 여백을 **1.5mm로 줄임** (기존 2mm 최소 간격 기준보다
     작음 — 배경색이 있는 실무 표준은 더 타이트하게 잡는다는 뜻으로 이해).
  2. **무테** — 테두리 없이 이미지가 셀을 꽉 채우는 경우(토끼 프레임 같은 것). 캐릭터를 분석할 필요
     없이, 셀/이미지의 바깥 사각형에서 **안쪽으로 1.5mm** 들어간 사각형이 곧 칼선.
- 이 구분을 도구의 기본 옵션으로 넣어야 함.

**수정 내용**:

1. **`core/image_style.py` (신규)** — `ImageStyle` enum(`LINE_ART`=선화, `BORDERLESS`=무테)과
   `generate_style_cutline()`. 선화는 기존 GrabCut 분리 + 실루엣을 바깥쪽으로 `margin_mm`만큼
   버퍼(기본 1.5mm); 무테는 아예 분리를 하지 않고 **셀/이미지 경계 사각형을 안쪽으로 `margin_mm`만큼
   음수 버퍼(erosion)** — Shapely의 `buffer()`가 음수 거리를 그대로 지원해서 같은 함수로 자연스럽게
   구현됨. 세이프티/칼선/블리딩 3단계나 최소 간격 자동 조정 없이, 지정한 숫자 하나를 그대로 씀(작가님이
   정확한 실무 숫자를 줬으니 임의로 더 올리지 않음).
2. **`core/interactive_cutline.py`에 `generate_cutline_by_style()` 추가** — 위 결과를 기존
   `render_preview()`/`export_svg()`가 그대로 받아쓸 수 있는 `CutlineResult` 형태로 감싸줌(오프셋은
   `cut` 하나만 존재).
3. **`gui/app.py`**: "4. 이미지 종류" 섹션 추가 — 선화/무테/직접 설정(기존 도무송 5종 + 세이프티·칼선·
   블리딩 방식) 라디오 버튼과 간격(mm, 기본 1.5) 입력칸. 선화·무테를 고르면 새 흐름을, "직접 설정"을
   고르면 기존 흐름을 그대로 사용 — 기존 사용자 흐름은 전혀 안 바뀜. 무테는 드래그 선택 없이도(이미지
   전체를 셀로 간주) 동작하고, 선화는 캐릭터를 가리키는 드래그 선택이 반드시 있어야 하며 없으면 명확한
   안내 메시지를 띄움. Xvfb로 세 가지 경로(무테/선화-선택있음/선화-선택없음 오류) 전부 직접 실행해서
   확인함.

**실제 파일로 검증** (`2조수희_5_유포지_유광코팅(cs6).ai`, 계속 이 파일로 작업):

- **무테(토끼)**: 이미지 내용을 전혀 분석하지 않고, 셀 경계 사각형에서 안쪽으로 1.5mm 들어간 사각형만
  계산 → 실제 손그린 사각형 칼선과 비교(경계선 기준, 캐릭터 기준 아님으로 다시 계산): 왼쪽/위/오른쪽/
  아래 각각 약 2.1~2.2mm 차이(내 1.5mm가 실제 손그린 선보다 살짝 바깥쪽) — 정확히 1.5mm는 아니지만
  같은 방향으로 비슷한 범위. 작가님이 준 1.5mm를 표준값으로 그대로 채택함. (`output/
  bunny_inset_compare.png`)
- **선화(곰 캐릭터)**: 같은 타일의 곰 캐릭터에 여백만 1.5mm로 바꿔서 다시 생성 → 실제 손그린 선과의
  IoU가 지난 시도의 0.53(2~4mm 여백)에서 **0.64로 개선** — 실무 표준(1.5mm)을 쓰니 실제 결과에 더
  가까워진다는 걸 정량적으로 확인. (`output/file2_lineart_1p5_compare.png`)
- 새 사본(`..._사본_자동칼선테스트.ai`, 원본에서 다시 새로 복사)에 `칼선(무테,1.5mm)`, `칼선(선화,
  1.5mm)` 두 레이어를 추가 — 원본 인쇄레이어 이미지 바이트 100% 동일, 기존 레이어 6개/기존 칼선 57개
  패스 전부 그대로 확인.

**다음에 할 일**:
- 무테 사각형의 정확한 기준 사각형("셀 경계")을 자동으로 알아내는 방법 — 지금은 호출하는 쪽에서
  `개별재단 레이어` 격자나 수동 좌표를 넘겨줘야 함. 드래그 선택 하나로 "이 칸 전체"를 자동 인식하게
  만드는 게 다음 단계.
- 선화 1.5mm도 실제로는 캐릭터마다 살짝 다를 수 있어(0.64 IoU면 아직 개선 여지 있음), GrabCut 정확도
  개선(다섯 번째 업데이트에서 남긴 과제)과 함께 계속 다듬을 것.

**전달**: 새 사본과 비교 이미지(`bunny_inset_compare.png`, `file2_lineart_1p5_compare.png`)는 실제
도안이라 저장소에 올리지 않고 작가님 컴퓨터 폴더/대화창으로만 전달. 저장소에는 코드(`core/
image_style.py` 신규, `core/interactive_cutline.py`의 `generate_cutline_by_style()`, `gui/app.py`의
이미지 종류 옵션)만 커밋.

## 여덟 번째 업데이트 — 선화/무테를 매번 고르지 않고 자동 감지, 새 파일(3조수희_인델눈송이)로 검증

**요청 배경**: "곰 이미지 안쪽 칼선은 선화가 아닌 무테, 곰이미지를 선화로 작업하면 바깥의 칼선 각각
1개씩 맞아" — 지난 회차에서 검증했던 `2조수희` 파일의 "곰 캐릭터"를 다시 짚어주신 것이었는데, 실제로
확인해보니 그 타일 안에는 곰/캐릭터가 **두 종류** 있었다: (1) 스케이트보드 타는 곰, 발레하는 곰 같은
자유형 캐릭터들 — 이건 각각 실루엣을 따라가는 선화 칼선이 맞고 실제로도 캐릭터당 하나씩 개별 선이었다.
(2) 회색 상자 안에 그네 타는 곰이 그려진 액자형 디자인 — 이건 실제로는 상자 자체의 사각형 테두리를
따라가는 **무테** 칼선이었다(내가 지난 회차에 이걸 곰 "캐릭터"로 착각해서 선화로 처리했었음). "다음 파일로
연습하자, 3조수희_5_유포지_인델눈송이(cs6) 학습해서 문제점 보완하자"는 지시에 따라 이 파일로 검증하고,
같은 문제(어떤 게 선화이고 어떤 게 무테인지 자동으로 구분하는 것)를 코드로 풀었다.

**실측(2조수희 실제 칼선레이어에서 직접 추출)**: PyMuPDF `get_drawings()`로 85~57개 실제 칼선 폴리곤을
좌표까지 그대로 뽑아서(`items`의 `re`/`l`/`c`를 베지어 평탄화해 링으로 복원) 인쇄레이어 이미지 위에
그대로 겹쳐봤다. 각 폴리곤의 "사각형도"(`area / minimum_rotated_rectangle.area`, 1.0이면 완벽한 직사각형)를
재보니:
- 회색 상자 곰(액자형): **0.879**
- 재사용되는 토끼 모서리 액자: **1.000**
- 그 외 모든 자유형 캐릭터(스케이트보드 곰, 발레 곰들, 강아지, 배추잎): **0.55~0.79**
깔끔하게 갈린다 — 0.85를 기준선으로 잡으면 두 그룹이 정확히 나뉜다.

**핵심 발견**: 이 "사각형도" 판정을 실제 손그린 선이 아니라, **우리 GrabCut 분리 결과 자체**에도 그대로
적용해봤더니 거의 똑같이 갈렸다(회색 상자 곰 분리 결과 0.8895 vs 실제 0.879, 스케이트보드 곰 분리 결과
0.727 vs 실제 0.666). 즉 아직 만들지도 않은 실제 칼선과 비교하지 않고도, "이 도안이 액자형(무테)인지
자유형 캐릭터(선화)인지"를 우리가 이미 갖고 있는 GrabCut 분리 결과의 모양만 보고 스스로 판단할 수 있다는
뜻 — 매번 라디오 버튼을 고르게 하지 않아도 되는 실질적인 자동화가 가능해짐.

**코드 변경**:
1. **`core/style_classify.py` (신규)** — `rectangularity(geom)`과 `classify_style(segmented_design,
   threshold=0.85)` → `ImageStyle.LINE_ART`/`BORDERLESS` + 측정값을 담은 `StyleClassification` 반환.
2. **`core/interactive_cutline.py`에 `generate_cutline_auto()` 추가** — 드래그 선택 영역을 GrabCut으로
   분리 → 그 모양으로 선화/무테 자동 판정 → **판정 후의 실제 선 자체는 기존에 검증된
   `generate_cutline_by_style()`에 그대로 위임**(직접 다시 만들지 않음). 이 위임이 중요한 이유: 처음엔
   무테로 판정된 경우 "분리된 내용물의 최소회전사각형"을 셀 경계로 썼었는데, 배경색이 연한 액자 디자인
   (아래 한계 참고)에서는 분리 자체가 셀 전체를 못 잡을 수 있어서 오히려 위험했다. 드래그한 선택 영역
   자체(`selection_px`)를 셀 경계로 쓰는 기존 방식이 훨씬 안전하다는 걸 확인하고 그쪽으로 정리했다
   (`core/image_style.py`의 무테 분기도 `bounds_px`보다 `selection_px`를 우선하도록 순서를 바꿈 —
   `bounds_px`는 원래 "못 넘어가는 바깥 한계"용으로 넓게 줄 수 있어서, 무테의 실제 셀 경계와 혼동하면
   안 됨).
3. **`gui/app.py`**: "이미지 종류" 라디오에 **"자동 감지"**를 추가하고 기본값으로 설정(선화/무테/직접
   설정은 그대로 남겨서 자동 판정이 틀렸다 싶으면 바로 수동으로 바꿀 수 있음). 자동 감지 결과 화면에
   `자동 감지: 선화 (사각형도 0.63, 기준 0.85)` 처럼 판정 근거를 그대로 보여줌 — 틀렸을 때 왜 틀렸는지
   바로 보이게. Xvfb로 실제 파일 이미지에 대해 드래그選택→자동감지→생성 전체 경로와, 선택 없이 자동감지를
   눌렀을 때의 오류 메시지 경로까지 직접 실행해서 확인함.

**실제 파일로 검증** (`3조수희_5_유포지_인델눈송이(cs6).ai`, 이번에 새로 학습):
- 라쿤형 캐릭터: 자동 판정 **선화**(사각형도 0.63) — 실제 손그린 선과 IoU **0.860**
- 강아지 캐릭터: 자동 판정 **선화**(사각형도 0.73) — IoU **0.680**
- `2조수희` 회색 상자 곰(재검증): 자동 판정 **무테**(사각형도 0.89) — IoU **0.879** (지난 회차에
  선화로 잘못 처리했던 바로 그 도안)
- `2조수희` 스케이트보드 곰(재검증): 자동 판정 **선화**(사각형도 0.73) — IoU **0.627**

**정직하게 밝혀둘 한계**: 재사용되는 토끼 모서리 액자(실제 사각형도 1.000, 완전한 무테 사례)는 자동
감지가 **틀렸다** — 사각형도 0.585로 측정되어 선화로 잘못 판정됨. 원인: 이 액자는 배경이 옅은 라벤더
색이라 GrabCut이 그 평평한 배경 채우기까지 전경으로 못 잡고 토끼+장식 모서리만 잡아버려서, 애초에
"분리된 모양"이 사각형과 거리가 멀어짐 — 실제 도안이 사각형이 아니어서가 아니라 GrabCut 분리 자체가
이 특정 색 대비에서 약하기 때문. 이런 경우엔 자동 감지 화면에 뜨는 낮은 사각형도 수치를 보고 수동으로
"무테"를 선택하면 되고, 그 경로(선택 영역 자체를 셀 경계로 쓰는 방식)는 별도 회귀 없이 그대로 정확하게
동작함 — 사본 파일에도 이 경우를 수동 설정으로 명시적으로 남겨서 왜 수동으로 바꿨는지 알 수 있게 해둠.

**새 사본** (`3조수희_5_유포지_인델눈송이(cs6)_사본_자동칼선테스트.ai`, 원본에서 새로 복사, 원본
이미지 바이트 100% 동일·기존 레이어 6개·기존 칼선 85개 패스 전부 보존 확인)에 레이어 3개 추가:
`칼선_자동감지(라쿤,선화,1.5mm)`, `칼선_자동감지(강아지,선화,1.5mm)`,
`칼선_수동설정(테두리모서리,무테,1.5mm,자동감지오탐)`.

**다음에 할 일**:
- 옅은/저대비 배경에서 GrabCut이 사각형 배경 채우기를 놓치는 문제 — 색상 대비가 약할 때의 폴백(예:
  선택 영역 가장자리 색 샘플링으로 배경 여부 판정) 검토.
- 다섯 번째 업데이트에서 남긴 GrabCut 바깥쪽 편향/erosion 불안정 문제는 여전히 미해결.
- 여러 도안이 섞인 한 타일을 한 번에 자동으로 나눠서(지금은 도안 하나씩 드래그) 처리하는 것도 다음
  단계 후보.

**전달**: 새 사본과 비교 이미지(`snowflake_auto_compare.png`)는 실제 도안이라 저장소에 올리지 않고
작가님 컴퓨터 폴더/대화창으로만 전달. 저장소에는 코드(`core/style_classify.py` 신규,
`core/interactive_cutline.py`의 `generate_cutline_auto()`, `core/image_style.py`의 우선순위 수정,
`gui/app.py`의 자동 감지 옵션)만 커밋.

## 아홉 번째 업데이트 — 선화/무테 정의 재확인 + 기존 칼선 여백 측정 기능

**요청 배경 1 (선화/무테 재정의)**: 실제 상업 굿즈 사진 4장을 보여주며 "선화는 테두리 선이 있는 그림이고
내 그림은 테두리 선이 없는 무테야"라고 정정해 주셨다. 산리오풍 할로윈 고양이/햄스터 캐릭터 시트, "FIND
THE VILLAIN" 시트처럼 캐릭터마다 굵은 테두리(흰색/검은색 아웃라인)가 그려져 있고 그 개별 캐릭터가 여백을
두고 떨어져 배치된 게 **선화**이고, 작가님 본인의 "공주토끼와 딸기" 실제 판매 시트처럼 테두리 없이 배경
패턴 전체를 캐릭터가 빈틈없이 채우는 그림이 **무테**라는 뜻이었다.

돌아보니 이건 지금까지 코드에 넣어둔 것과 실제로 모순되지 않는다 — 오히려 왜 두 처리 방식(선화=캐릭터
실루엣 바깥쪽/각각 하나씩, 무테=셀 사각형 안쪽)이 나뉘는지에 대한 **원인**을 알려주신 것이다: 테두리가
이미 그려진 캐릭터는 그 자체로 독립된 컷아웃으로 인쇄되니 실루엣을 따라 바깥쪽에 칼선을 두르는 게 맞고,
테두리 없이 화면 전체를 채우는 패턴은애초에 "캐릭터 하나의 경계"라는 게 없으니 셀 사각형 자체가 기준이
되는 것. `core/image_style.py` 상단 설명을 이 기준(테두리 유무를 먼저 눈으로 확인)으로 다시 썼다 —
로직 자체는 바뀌지 않음, "왜 이렇게 나뉘는지"를 정확한 말로 다시 적어둔 것.

**요청 배경 2 (기존 칼선 검사 기능)**: "기존 칼선 검사 하는 기능 실제로 필요해 작가들은 업체마다 다른
간격을 일일이 하나씩 확인하거든 좋은 방향이야" — 여섯/일곱 번째 업데이트에서 "다음 후보"로만 적어뒀던
아이디어(README의 "기존 칼선 자체를 검사하는 기능")를 실제로 만들어달라는 확인이었다. 실무에서 인쇄
업체마다 요구하는 칼선 여백이 달라서, 업체가 준 견본 파일을 열어 자로 하나하나 재보는 대신 자동으로
측정해주는 도구가 필요하다는 것.

**만든 것**:
1. **`core/ai_cutline_reader.py` (신규)** — 지금까지 스크래치 스크립트로만 하던 작업("실제 .ai 파일의
   칼선레이어에서 진짜 손그린 칼선 좌표를 그대로 꺼내오기")을 정식 모듈로 옮김. `load_real_cutlines(ai_path,
   ...)`가 인쇄레이어의 원본 래스터 이미지와, 칼선레이어의 모든 실제 도형을 **같은 이미지 픽셀 좌표계**로
   반환 -- 베지어 곡선(`c`)/직선(`l`)/사각형(`re`) 패스를 실제 좌표로 복원해서 만듦. 읽기 전용(파일을
   수정하지 않음).
2. **`core/margin_inspector.py` (신규)** — 기존의 모든 생성기가 "mm를 입력받아 칼선을 만드는" 방향이라면,
   이건 정반대: **이미 있는 칼선에서 mm를 역산**함. `measure_margin_mm(design, cutline, dpi)`가 칼선
   테두리를 따라 96개 지점을 고르게 뽑아 각 지점에서 실제 도안 경계까지의 거리를 재고, mm 단위
   평균/중앙값/최소/최대/표준편차로 보고. `measure_margin_from_image()`는 도안 실루엣을 아직 안 뽑았을 때
   칼선의 바운딩 박스를 드래그 선택처럼 써서 GrabCut으로 자동 분리까지 해줌.
3. **`inspect_cutline_margins.py` (신규, 프로젝트 루트)** — 실제 사용 진입점.
   `python inspect_cutline_margins.py "파일.ai"` 한 줄로 그 파일의 모든 실제 칼선을 크기순으로 나열하고
   각각의 중앙값/평균/최소/최대/편차(mm)와 선화·무테 판정을 표로 보여줌.

**실제 두 파일로 검증**:
- `2조수희_5_유포지_유광코팅(cs6).ai`: 작은 꽃/이파리류 도형들(회색 상자 곰 등 포함) 대부분 중앙값
  1.2~1.7mm, 편차 0.6~0.8mm로 상당히 일관됨 -- 실무 표준으로 확인된 1.5mm와 잘 맞아떨어짐.
- `3조수희_5_유포지_인델눈송이(cs6).ai`: 라쿤 캐릭터(7곳) 중앙값 2.6~3.4mm, 편차 0.65~0.74mm로 일관되게
  측정됨 -- 유광코팅 파일보다 이 파일의 실제 여백 관행이 조금 더 넓다는 것도 수치로 드러남(업체/도안마다
  다른 간격을 확인하고 싶다는 요청 배경과 정확히 맞아떨어지는 사례).
- **한계, 정직하게 확인됨**: 재사용되는 토끼 모서리 액자(두 파일에 공통, 실제로는 1.5mm 안팎의 무테
  사각형)는 여기서도 중앙값 6.5mm 근처로 잘못 측정됨 -- 다섯/여덟 번째 업데이트에서 이미 확인한 것과 같은
  원인(GrabCut이 옅은 배경색을 못 잡음). `--top` 출력에서 편차(std)가 유독 크게 나온 항목들이 바로 이런
  측정 신뢰도가 낮은 경우였고, 실제로 그 항목들을 눈으로 다시 확인하라고 안내 문구에 넣어둠.

**다음에 할 일**:
- GUI에는 아직 연결 안 됨(스크립트 레벨) -- "파일 열기 → 칼선 목록 → 여백 표" 형태로 GUI에 넣는 게
  다음 단계.
- 저대비 배경 GrabCut 한계(다섯/여덟 번째 업데이트에서 반복 확인됨)를 실제로 풀기 전까지는, 편차가 큰
  항목은 이 도구가 "여기는 눈으로 확인하세요"라고 알려주는 것 이상은 못 함 -- 근본 해결은 아직 미해결.

**전달**: 이번엔 실제 이미지/사본 파일을 새로 만들지 않음 -- 콘솔에 찍힌 측정 수치(평균/중앙값 등, mm
단위 숫자일 뿐 이미지 아님)만 대화창으로 공유. 저장소에는 코드(`core/ai_cutline_reader.py`,
`core/margin_inspector.py`, `inspect_cutline_margins.py`, `core/image_style.py`의 설명 수정,
`core/cutline_core.py`의 `px_to_mm()` 추가)만 커밋.

## 열 번째 업데이트 — 세 번째 실제 파일(4조수희_인델샌드스타)로 실전 연습, 새 코드 없이 검증만

**요청 배경**: "개념을 이해했으니 실전 연습으로 보완하자. 4조수희_5_유포지_인델샌드스타(cs6) 이걸로
연습해 토끼 이미지는 사각 도무송인거 잊지 말고. 이건 펄 효과가 있어서 이미지 개체 구분하기 어려울거야.
천천히 시도해." -- 새 기능을 만들기보다, 지금까지 만든 자동 감지·여백 측정 기능이 **세 번째로 완전히
다른 실제 파일**에서도 실제로 통하는지 천천히 하나씩 확인하는 회차. 코드는 바꾸지 않고 검증만 함.

**파일 구조**: 이번에도 동일한 6개 OCG 레이어, 인쇄레이어 이미지 1장, 칼선레이어 실제 도형 43개. 이번
시트는 보라색 배경에 노랑/청록/크림색 물방울 무늬("펄/샌드스타" 느낌)가 깔려 있고, 그 위에 캐릭터
5종(곱슬머리 소녀, 푸들 캐릭터, 곰 캐릭터, 여우/고양이귀 캐릭터, 열매 넝쿨)과 "Pu_dle" 텍스트 라벨,
그리고 이미 앞선 두 파일에서 본 것과 동일한 토끼 모서리 액자가 반복 배치되어 있음.

**직접 확인해보니 예상과 달랐던 점**: "펄 효과라 어려울 것"이라는 예상과 달리, 이 파일이 지금까지 중
**가장 안정적으로** 측정됐다. 이유를 살펴보니, 이 시트의 캐릭터 5종은 전부 흰색 또는 민트색의 **또렷한
테두리 선이 이미 그림에 그려져 있어서**(아홉 번째 업데이트에서 정리한 "선화=테두리 있음" 그 자체) 물방울
배경이 아무리 알록달록해도 GrabCut이 캐릭터 경계를 잡기가 오히려 쉬웠던 것으로 보인다. 물방울 배경의
"복잡함"이 문제를 만드는 게 아니라, 테두리 유무가 진짜 변수라는 걸 다시 한번 확인한 셈.

**실측 (`inspect_cutline_margins.py`로 43개 전부 스캔)**:
- 소녀/푸들/곰/여우/넝쿨 캐릭터(총 29개 도형): 중앙값이 대부분 **1.0~1.3mm**, 편차(std)도 대부분
  0.3~0.7mm로 매우 일관됨 -- 지금까지 본 세 파일 중 가장 좁고 안정적인 분포. 이 파일(업체?)의 실제
  칼선 관행은 작가님이 알려주신 일반 표준(1.5mm)보다 살짝 타이트한 약 1.1mm 근처라는 것도 수치로 드러남.
- 넝쿨 하나(7개 중 1개)만 중앙값 3.57mm에 편차 2.49mm로 확 튀었음 -- 표에 편차 수치로 자동으로
  드러나서 "이 항목은 눈으로 재확인하라"는 신호가 정확히 작동한 사례.
- "Pu_dle" 텍스트 라벨(흰 붓터치 배경, 7개 반복): 전부 **무테**로 자동 판정됨(사각형도 0.9 안팎) --
  라벨 자체엔 테두리 링이 따로 없고 붓터치 배경 하나로 끝나는 디자인이라, "테두리 유무" 기준으로도
  무테가 맞음. 실제 여백도 캐릭터들(1.0~1.3mm)보다 확실히 좁은 0.55~0.72mm로, 라벨류는 캐릭터류와
  실제 관행 자체가 다르다는 것도 이 도구로 처음 구분해냄.
- **토끼 모서리 액자 재확인**: 이번에도 다섯/여덟/아홉 번째 업데이트와 똑같은 원인(배경색이 옅어
  GrabCut이 못 잡음)으로 자동 감지가 선화로 잘못 판정되고 여백도 6.5mm 근처로 과대 측정됨 -- 새로운
  문제가 아니라 이미 알고 있는 한계가 세 번째 파일에서도 똑같이 재현된 것. 다만 "토끼는 사각
  도무송(무테)"이라는 이해 자체는 여전히 맞고, 수동으로 무테를 선택하면 정확하게 처리됨(여덟 번째
  업데이트에서 이미 검증).
- 자동 생성 칼선과 실제 칼선을 겹쳐 그려서 비교 -- 소녀/푸들/곰/여우/넝쿨/라벨 전부 육안으로도 거의
  겹쳐 보임, 토끼 모서리만 살짝 벌어짐(위 한계 그대로).

**결론**: 새로 고칠 코드는 없었음 -- 이번 회차는 지금까지 만든 기능(자동 감지, 여백 측정)이 완전히 다른
세 번째 실제 파일에서도 일관되게 통한다는 걸 확인한 순수 검증 회차. "펄 효과라 어려울 것"이라는 짐작이
틀렸다는 것도 정직하게 기록해둠 -- 실제로 어렵게 만드는 건 배경의 복잡도가 아니라 여전히 저대비
배경(토끼 액자)이었다.

**전달**: 실제 도안 비교 이미지(`sandstar_auto_compare.png`)와 측정 수치는 대화창으로만 전달, 저장소엔
올리지 않음. 이번 회차는 코드 변경이 없어서 저장소에 새로 커밋할 파일도 없음.

## 열한 번째 업데이트 — 네 번째 실제 파일(5조수희_인델별) 한 판 전체 칼선 재생성 + 밀림 범위 계산 + 회전 배치 대응

**요청**: "5조수희_5_유포지_인델별(색감 수정) 칼선 이번에 한판을 전부 다시 그려봐. 그리면서 모서리 부분을
잘 마무리하고 밀림 예상 범위 계산 해서 칼선 넣어. 추가로 자동으로 칼선 역추적해서 간격 확인하는 것도
테스트하고 디벨롭해." -- 지금까지는 파일 하나에서 캐릭터 몇 개만 골라 검증했는데, 이번엔 **시트 전체**의
칼선을 실제로 새로 그려보라는 요청. 추가로 "밀림"(인쇄와 커팅 사이 등록 오차)을 감으로 정하지 말고
계산해서 넣으라는 것, 그리고 기존 칼선 여백 역측정 기능(아홉 번째 업데이트)을 계속 발전시키라는 것.

**이번 파일이 지금까지와 근본적으로 달랐던 점**: 처음으로 이미지가 **2장** 박혀 있었음(반복 무늬 타일
1772x945px, 토끼 모서리 액자 1299x945px) -- 그리고 타일이 7번 배치되는데 그중 **1번은 90도 회전**되어
시트의 남는 모서리 공간에 끼워져 있었고, 토끼 액자도 회전 배치였음. 지금까지 만든 모든 코드
(`ai_cutline_reader.py`, `ai_layer_export.py`)는 "이미지 한 장, 회전 없는 단순 확대/축소 배치"만
가정하고 있어서 이 파일엔 그대로 못 씀 -- `page.get_image_rects(xref, transform=True)`로 실제 배치
행렬(a,b,c,d,e,f)을 직접 꺼내보니 회전된 인스턴스만 b,c 값이 0이 아닌 것으로 확인됨.

**만든 것**:
1. **`core/image_placement.py` (신규)** -- 회전까지 포함하는 일반 픽셀↔페이지좌표 변환. PyMuPDF
   자신의 매트릭스 표기(a,b,c,d,e,f)를 그대로 필드명으로 써서, `page.get_image_rects(..., transform=True)`
   결과를 그대로 넣고 쓸 수 있게 함. 실제 회전된 배치(7번째 타일)로 4개 꼭짓점이 정확히 들어맞는지,
   역변환(point_to_pixel)이 정확히 원래 좌표로 돌아오는지 직접 검증함.
2. **`core/repeat_grid.py`에 `replicate_by_placements()` 추가** -- 기존 `replicate_by_offsets`는 평행
   이동만 가능했는데(회전 없음), 이번엔 회전된 인스턴스가 있어서 새 함수로 각 배치의 실제 행렬을 통해
   타일 하나짜리 칼선을 7곳(회전 포함) 전부에 정확한 방향으로 투영.
3. **`core/ai_layer_export.py`에 `add_point_space_layer_to_ai()` 추가** -- 기존 함수는 "이미지 한 장 +
   단순 배치 사각형" 하나를 가정하고 픽셀→페이지좌표 변환까지 대신 해줬는데, 이번 결과물은 이미
   서로 다른 배치 행렬 7+1개를 거쳐 페이지 좌표로 매핑된 상태라 공유 가능한 단일 사각형이 없음. 그래서
   이미 페이지 좌표로 매핑된 도형을 그대로 그려 넣는 버전을 새로 만듦.
4. **`core/slip_margin.py` (신규)** -- "밀림 예상 범위"를 감이 아니라 실측으로 계산. 방법: 실제로 이미
   승인되어 쓰이고 있는 손그린 칼선(타일0의 실제 칼선레이어 12개 요소, `core/margin_inspector.py`로
   96개 지점씩 측정)의 **점마다 여백이 흔들리는 정도(표준편차)** 자체를 "이 작가의 실제 인쇄/커팅
   공정이 실제로 얼마나 밀리는지"의 직접적인 증거로 씀. 측정된 편차: 요소별 중앙값 0.66~1.95mm, 표준편차
   평균 0.40mm, 최대 0.76mm. `slip_allowance_mm = 2.0 x 관측된 최악의 편차(0.76mm) = 1.52mm`를 기존
   1.5mm 기본 여백에 더해 최종 여백 **3.02mm**를 이번 재생성에 사용. 12개 표본짜리 단일 파일 데이터라
   통계적으로 엄밀하진 않다는 것, 그리고 왜 "최악값 x 2배"라는 보수적인 선택을 했는지 모듈 설명에
   정직하게 적어둠 -- 다음 파일들에서 더 큰 편차가 나오면 이 값 자체를 다시 조정해야 함.

**실행 결과** (`scratch/build_full_sheet.py`, 저장소엔 안 올림):
- 타일 하나(1772x945px)의 실제 칼선 12개 위치를 참고해 각각 자동 감지(선화 10개/무테 2개) + 3.02mm
  여백으로 새 칼선 생성. 토끼 액자는 GrabCut 자체가 안 되는 케이스(선택 영역이 이미지 전체라 "배경"으로
  삼을 여백이 없어 에러) -- 이건 이미 알려진 저대비 배경/전체 채움 무테 케이스(다섯째 업데이트 이후 계속
  확인됨)라서, 자동판정을 우회하고 바로 무테로 지정해서 생성(근거: 실제 배경이 연보라색 무테 전체 채움
  디자인인 것을 이미지로 직접 확인함).
- 타일용 12개 칼선을 `replicate_by_placements()`로 7곳(6곳 정방향 + 1곳 회전)에, 토끼 칼선을 자기 배치
  행렬로 1곳에 투영 → 페이지 좌표 도형 총 92개(요소 하나가 자연스럽게 2조각으로 나뉘는 경우 포함, 85개
  아님에 오해 없도록 확인함: 92 = 12요소x7곳 + 2조각짜리 1요소 보정 + 토끼 1개).
- 사본 파일에 새 레이어(`칼선레이어_전체재생성(3.02mm)`)로 추가 후, 인쇄레이어만/기존 칼선만/새 칼선만/
  겹쳐서 4가지로 각각 렌더링해서 육안 비교. 회전된 7번째 타일도 방향이 정확히 맞물려 나옴(찌그러짐/
  미러링 없음), 시트 전체 이음매(타일 경계)에서도 어색한 끊김 없음, 모서리(라운드 join)도 매끈함 --
  "모서리 부분을 잘 마무리"라는 요청을 시트 레이아웃상의 남는 모서리(회전 타일+토끼) 처리로 해석해서
  확인한 것.
  - (기술 메모: PyMuPDF에서 OCG on/off를 바꾼 뒤 바로 `get_pixmap()`을 부르면 반영이 안 되고, 한 번
    저장(`saveIncr()`) 후 다시 열어야 반영되는 것을 이번에 확인함 -- `set_layer()`가 PDF의 `/D` 설정은
    바로 바꾸지만 렌더러가 그 변경을 파일을 다시 열 때만 읽어들이는 것으로 보임.)

**다음에 할 일**:
- `slip_margin.py`의 계산은 이번 파일 하나에서 나온 12개 표본 기준 -- 다른 업체/파일에서 계속
  `inspect_cutline_margins.py`로 검증하면서 이 값이 맞는지 계속 확인해야 함.
- `replicate_by_placements()`는 여전히 호출하는 쪽이 실제 배치 행렬 목록을 직접 넘겨줘야 함(자동으로
  같은 이미지의 반복 배치를 찾아주진 않음) -- 이건 `core/repeat_grid.py`의 기존 평행이동 버전과 같은
  한계.
- 새 칼선(92개 도형)이 전부 유효한 폴리곤인지, 겹치는 인접 도형끼리 자동으로 병합해야 할지는 아직 눈으로
  본 것 이상의 정량 검증(예: self-intersection 검사)은 안 함.

**전달**: 실제 파일 복사본(`5조수희_인델별_전체칼선_재생성.ai`, 새 칼선 레이어 포함)과 비교 이미지 4장은
대화창/작가님 컴퓨터로만 전달(바이트 검증 후). 저장소에는 코드만 커밋: `core/image_placement.py`(신규),
`core/slip_margin.py`(신규), `core/repeat_grid.py`(`replicate_by_placements` 추가),
`core/ai_layer_export.py`(`add_point_space_layer_to_ai` 추가).

## 열두 번째 업데이트 — 위 결과 실제로 탈락, 3가지 사유로 수정

**작가님 피드백 (그대로)**: "칼선이 이중으로 들어감 간식 파츠를 인식하지 못하고 단일 칼선과 규격도
틀림", "햄스터 칼선이 폭이 넓어 빨간색 칼선에서 적어도 절반 간격으로 좁히고 그러면서 전체 칼선의 모양이
뾰족하지 않게 모서리르 둥글게 부피는 적게", "토끼 그림은 무테로 분류 하는게 아니라 나한테 먼저 도무송용인지
묻고, 어떤 형태의 도무송인지 완칼인지 사각형인지 원형인지 확인하고 사각형 도무송으로 만들어야지" -- 열한
번째 업데이트 결과물이 실사용 기준으로 **탈락**. 바로 앞 회차 "다음에 할 일"에 적어둔 "새 칼선이 전부
유효한 폴리곤인지 검증 안 함"이 정확히 문제가 된 사례였다.

**원인 진단 (짐작하지 않고 실제로 다시 GrabCut을 돌려서 확인)**:
1. **이중 칼선**: 타일 12개 요소를 하나씩 다시 세그멘테이션해서 살펴보니, 그중 2개는 GrabCut 마스크에
   본 도안엔 없는 아주 작은 구멍(857px²/1302px², 전체 도안 대비 0.6~0.9%)이 생겨 있었고, 1개는 진짜
   도안과 별개로 71px²짜리 먼지 같은 조각(전체 대비 0.06%)이 따로 잡혀 있었음. `core/cutline_core.py`의
   `_contours_to_polygons`는 지금까지 구멍을 무조건 다 보존했고(도넛 모양 같은 진짜 구멍을 위해), 작은
   파편도 절대 면적 25px² 기준만 걸러서 통과했던 것 -- 그래서 이 노이즈가 그대로 바깥쪽으로 버퍼링되어
   원래 칼선 옆에 작은 선/고리가 하나 더 그려진 것("이중 칼선")이었다.
2. **여백 폭/뾰족함**: 열한 번째 업데이트에서 계산한 밀림 여백(3.02mm = 1.5mm + 2×0.76mm)이 실제로
   빨간 선 대비 너무 넓었고, 큰 여백으로 버퍼링할수록 위 1번 노이즈나 자잘한 픽셀 계단이 뾰족한 돌기로
   증폭되는 것도 같이 확인됨.
3. **토끼 모서리**: 지난 회차엔 재사용되는 무테 액자라는 과거 패턴을 근거로 스스로 판단해서 바로
   생성했는데, 이번엔 그렇게 하지 말고 도무송 여부/형태를 먼저 확인받으라는 지적.

**고친 것**:
1. `core/cutline_core.py`의 `_contours_to_polygons`에 `min_hole_area_ratio`(기본 2%) 추가 -- 자기
   외곽선 면적의 2% 미만인 구멍은 노이즈로 보고 메움. 이미 검증된 진짜 도넛형 구멍(README "구멍이 있는
   도안" ✅)은 자기 외곽 대비 훨씬 큰 비율이라 영향 없음.
2. `core/segmentation.py`의 `segment_design_in_region`에 상대 면적 필터 추가 -- 가장 큰 조각의 2%
   미만인 분리된 파편은 절대 면적 기준(25px²)을 통과하더라도 버림.
3. `core/image_style.py`의 LINE_ART 경로에 메인 여백 버퍼링 **전에** 작은 왕복 버퍼(0.3mm 아웃→인,
   라운드 join)를 추가해 잔여 픽셀 노이즈를 먼저 매끈하게 다듬고, 메인 버퍼의 `resolution`도 16→24로
   올려 곡선을 더 부드럽게.
4. `core/slip_margin.py`의 `DEFAULT_SAFETY_FACTOR`를 2.0 → **1.0**으로 낮춤(최악 편차를 2배가 아니라
   1배만 추가) -- 최종 여백 3.02mm → **2.26mm**. 왜 2.0을 골랐었는지/왜 1.0으로 낮췄는지 모듈 설명에
   피드백 그대로 남겨둠(다음에 다른 파일에서 더 큰 편차가 실측되면 그때 그 근거로 다시 올릴 것).
5. 토끼 모서리는 **이번 재생성에서 아예 제외** -- 도무송/완칼 여부와 형태(사각/원형/타원형)를 작가님께
   먼저 여쭤보고, 확인 후에 넣기로 함(대화창에서 직접 질문).

**재확인**: 고친 코드로 타일 12개를 다시 생성해보니 92개(11번째 업데이트, 파편/구멍 포함)가 아니라 정확히
84개(12요소×7곳, 파편 없음)로 나옴 -- 노이즈가 사라졌다는 것을 개수로도 확인. 인쇄레이어+기존 칼선+새
칼선을 겹친 렌더링을 다시 비교해보니, 문제였던 요소들에서 이중 고리/파편이 사라졌고, 빨간 선과 파란 선
사이 간격도 눈에 띄게 좁고 일정해졌으며, 이전에 비해 모서리도 더 매끈함.

**다음에 할 일**: 토끼 모서리 답변 받으면 이번 파이프라인에 그대로 붙여서 완성. 2.26mm도 여전히 단일
파일 기준 -- 계속 다른 파일로 검증 필요.

**전달**: 수정판 사본(`..._전체칼선재생성_v2.ai`)과 겹침 비교 이미지는 대화창/작가님 컴퓨터로 바이트
검증 후 전달. 이전 회차의 탈락한 사본(`..._전체칼선재생성.ai`, "_v2" 없는 파일)은 작가님 컴퓨터에 그대로
남아있음 -- 필요 없으면 직접 지워도 되는 파일이라고 안내함. 저장소에는 코드만 커밋:
`core/cutline_core.py`(`min_hole_area_ratio`), `core/segmentation.py`(상대 파편 필터),
`core/image_style.py`(사전 스무딩 + resolution 상향), `core/slip_margin.py`(`safety_factor` 1.0로
조정).

**토끼 모서리 확인 후 마무리**: "토끼는 나한테 먼저 물어보고" 요청대로, 도무송/완칼 여부와 형태를 직접
여쭤봤고 "사각형 도무송"으로 확인받음. `core/cutline_types.py`의 도무송 4종 개념 중 정사각형/직사각형에
해당 -- 이 디자인은 배경이 자기 셀 가장자리까지 꽉 채워 인쇄되는(bleed) 형태라, 캐릭터 실루엣 기준으로
바깥쪽에 사각형을 씌우는 일반적인 도무송 방향과 달리 셀 전체 경계를 기준 사각형으로 삼아 표준 여백만큼
안쪽으로 넣는 것이 맞음(`core/image_style.py`의 BORDERLESS 경로와 결과적으로 동일한 계산 -- 다만 이번엔
확인받은 사각형 도무송으로 명시적으로 적용, 과거처럼 사각형도 점수로 조용히 추측한 게 아님). 같은
2.26mm 여백으로 생성해 12개 타일 요소(84개) + 토끼(1개) = **85개**로, 실제 파일의 손그린 칼선 개수와
정확히 일치. 최종 사본(`..._전체칼선재생성_v3.ai`)으로 전달 완료(바이트 검증).

## 열세 번째 업데이트 — 작은 액자형 요소가 스티커 안으로 파고드는 오류 추가 수정

**작가님 피드백 (그대로)**: "작은 요소들은 칼선을 만들 수 있다면 원본 이미지 외곽라인을 따라서 칼선
작업을 해야해. 근데 지금 씨리얼 모양은 칼선 오류가 있어. 칼선이 스티커 안에 들어가 있어." -- v3에서
초록 줄무늬/체크무늬 작은 액자형 장식 2개(사각형도 0.87~0.91로 무테 판정됐던 요소들)의 칼선이 실제
스티커 그림보다 안쪽으로 들어가 있었다는 지적.

**원인 진단**: 두 요소를 다시 세그멘테이션해서 직접 재보니, 선택 영역과 실제 세그멘트된 내용 사이에
사방으로 진짜 여백(2.6~12.9px, 다른 캐릭터들과 똑같이 각자 자기만의 배경/할로가 있음)이 있었음 -- 즉
"경계선 없이 셀 전체를 채우는" 무테가 전혀 아니라, 그냥 모양 자체가 네모난 선화(캐릭터 하나+할로)였던
것. 그런데 지금까지의 자동 판정은 사각형도 점수만 보고 무테로 잘못 결정했고, 무테로 결정되면 곧바로
"선택 영역 자체를 여백만큼 안쪽으로 인셋"하는 경로로 넘어가는데, 이 작은 요소는 선택 영역이 실제
그림보다 커서(할로 포함) 그 인셋 결과가 진짜 그림 안쪽으로 파고든 것이었음.

**고친 것**: `core/style_classify.py`의 `classify_style`에 "할로 우선 판정"을 추가 -- 세그멘테이션된
내용과 선택 영역 사이에 사방으로 실제 여백(2px 이상)이 있으면, 사각형도 점수가 아무리 높아도 무조건
선화로 판정하도록 사각형도 검사보다 먼저 확인. 사각형도는 할로가 전혀 없는(선택 영역 가장자리까지
내용이 닿는) 진짜 셀-전체-채움 케이스에서만 최종 결정에 사용됨 -- 2조수희의 액자형 곰(진짜 무테)은
여전히 무테로, 이번 파일의 작은 장식 2개는 이제 선화로 정확히 갈림. `core/interactive_cutline.py`의
`generate_cutline_auto`도 이 selection_px를 함께 넘기도록 연결.

**재확인**: 고친 코드로 타일 12개를 전부 다시 생성하니 12개 전부 선화로 판정됨(문제였던 2개 포함) --
개수는 여전히 85개(12x7+토끼1) 그대로 유지. 겹침 렌더링으로 두 장식 요소를 확대해서 확인해보니 파란
선이 이제 빨간 실제 선처럼 그림 바깥쪽을 정확히 두르고 있음(더 이상 안쪽으로 파고들지 않음).

**전달**: 최종 사본(`..._전체칼선재생성_v4.ai`)과 비교 이미지는 대화창/작가님 컴퓨터로 바이트 검증 후
전달. 저장소에는 `core/style_classify.py`(할로 우선 판정 추가)와 `core/interactive_cutline.py`
(selection_px 전달) 커밋.

## 열네 번째 업데이트 — 작은 소품류는 실루엣이 아니라 "사각형으로 트리밍"이 맞는 모델이었음

**작가님 피드백 (그대로)**: "그래도 작은 요소들은 칼선이 일반 칼선과 다르게 이미지 아웃라인 안 쪽으로
파고들어서 원 칼선처럼 이미지 일부를 재단해 재단 된 이미지를 스티커로 사용하는거야. 다시 해" -- 열세
번째 업데이트(할로 우선 판정)로도 여전히 부족했다는 뜻. 실제 인쇄는 이런 작은 소품(패턴 조각)을 필요한
크기보다 넉넉하게 찍어두고, 칼선은 그 안에서 정해진 사각형만큼만 "잘라내서" 그 잘린 부분을 스티커로
쓰는 방식이라는 걸 알려주심 -- 실루엣을 따라가는 개념 자체가 이 소품류에는 안 맞는 것이었다.

**재진단**: 열세 번째 업데이트의 "할로" 신호(세그멘트 결과와 선택 영역 사이의 진짜 여백)는 논리적으론
맞았지만, 애초에 GrabCut이 체크무늬/줄무늬처럼 저대비 경계가 반복되는 작은 패턴을 정확히 못 잡는다는
이 프로젝트의 오래된 한계(토끼 액자 케이스와 같은 원인)가 여기서도 그대로 작동한 것 -- 그래서 실루엣을
기준으로 바깥쪽에 여백을 줘도, 세그멘트 자체가 진짜 인쇄 경계보다 작게 잡혀 있어 결과가 여전히 진짜
그림 안쪽에 걸렸다. 근본 원인은 "판정을 무테로 하느냐 선화로 하느냐"가 아니라 애초에 이런 소품류엔
GrabCut 실루엣이라는 개념 자체를 적용하면 안 된다는 것.

**고친 것**: `core/interactive_cutline.py`에 `_rect_trim_cutline()`과 `generate_cutline_auto`의
`small_element_max_dim_mm` 파라미터를 추가. 선택 영역의 긴 변이 이 기준(mm) 이하면 세그멘테이션/
스타일판정을 아예 건너뛰고, 선택 영역 사각형 자체를 그대로 밀림 여백만큼 바깥으로 버퍼링 -- 실루엣을
전혀 참고하지 않으므로 GrabCut의 저대비 한계에 애초에 영향받지 않음. 실제 파일에서 캐릭터(7개, 전부
25.9mm 이상)와 소품(5개, 전부 14mm 이하)의 크기가 깔끔하게 갈려서, 기준값 20mm를 기본값으로 둠.

**재확인**: 12개 요소 중 소품 5개(초록·체크 패턴, 매화, 누룽지, 아몬드 모양)는 이제 전부 "소형 요소"로
분류되어 사각형 트리밍 처리, 나머지 7개 캐릭터는 그대로 실루엣 처리. 겹침 렌더링에서 두 패턴 소품을
확대해보니 파란 사각형이 빨간 실제 선을 완전히 감싸며, 더 이상 그림 패턴 안쪽으로 들어가지 않음.
전체 개수도 여전히 85개 그대로.

**전달**: 최종 사본(`..._전체칼선재생성_v5.ai`)과 비교 이미지는 대화창/작가님 컴퓨터로 바이트 검증 후
전달. 저장소에는 `core/interactive_cutline.py`(`_rect_trim_cutline`, `small_element_max_dim_mm`)
커밋.

## 열다섯 번째 업데이트 — 소형 요소는 "네모"가 아니라 실제 모양대로, + 서로 다른 요소 간 2mm 간격을 최우선 규칙으로 강제

**작가님 피드백 (그대로)**: "틀렸어, 작은 요소들은 요소들의 이미지 형태 그대로 칼선을 만들어야해. 원본
칼선과 비교 하면서 뭐가 다르고 차이점이 왜 발생하는지 분석하고 적용해. 작은 요소 모두 네모 칼선으로
기존의 큰 요소의 칼선과 겹치잖아. 칼선간 간격 2mm는 필수 규칙이야. 이걸 틀리면 안 돼. 그 어떤 법칙보다
우선 순위에 둬야해" -- 열네 번째 업데이트(사각형 트리밍)로 "안쪽으로 파고드는" 문제는 없어졌지만, 두
가지가 새로 지적됨: (1) 소품은 네모가 아니라 실제 그림 모양 그대로 칼선이 나와야 한다, (2) 소품의
네모 칼선이 바로 옆 큰 캐릭터의 칼선과 겹쳤다 -- 그리고 요소 간 최소 2mm 간격은 그 무엇보다 우선하는
필수 규칙이라고 명시.

**원본 칼선과 직접 비교한 진단**: 문제였던 두 소품(초록 줄무늬, 분홍 체크무늬)의 실제 원본 그림을
그대로 잘라 눈으로 보고(`scratch/raw_crop_elem2.png`, `raw_crop_elem8.png`), 실제 손그린 칼선
폴리곤과 GrabCut 세그멘트 결과를 같은 크롭 위에 겹쳐 그려봄(`scratch/overlay_elem2.png`,
`overlay_elem8.png`, 빨강=실제 칼선/파랑=세그멘트). 결과: 이 두 소품은 알록달록한 패턴(줄무늬/체크)이
그 자체의 연한 베이지색 둥근 사각형 "받침/마운트" 위에 올라가 있는 이중 구조였고, 실제 칼선(빨강)은
패턴이 아니라 그 받침 전체의 바깥 둘레를 두르고 있었음. 반면 GrabCut(파랑)은 대비가 강한 패턴만
전경으로 잡고, 받침은 통째로 놓치고 있었음 -- 실제 칼선과 세그멘트 사이의 간격(4~13px)이 정상적인
선화 여백(할로)치고는 너무 좁아서, "여백을 뺀 나머지가 진짜 그림"이 아니라 "그림 일부(받침)를 통째로
못 찾은 것"이라는 뜻이었음.

**왜 못 찾는지 추가로 검증**: 이게 GrabCut만의 문제인지 확인하려고 두 가지를 더 시도함.
(1) GrabCut에 "확실한 전경" 시드를 패턴 중앙에 강제로 심어서 재시도(`scratch/test_grabcut_fix.py`) --
결과가 한 치도 안 바뀜. GrabCut의 그래프컷은 항상 주변에서 가장 대비가 강한 경계(패턴↔받침)에 달라붙지,
더 약한 경계(받침↔배경)는 트림 시딩과 무관하게 무시한다는 것 확인.
(2) 순수 픽셀 색상 거리로 배경과 구분 시도(`scratch/test_colordist.py`) -- 받침의 실측 색상
(BGR≈193,224,243)이 주변 장면 배경의 실측 평균(≈176,215,239, 표준편차 46/24/14)과 사실상 겹침 --
즉 이 두 요소는 받침과 배경이 실측 색상값 자체가 구분 불가능할 만큼 비슷해서, 어떤 픽셀 기반 방법으로도
진짜 바깥 경계를 잡아낼 수 없다는 게 세 번째로, 이번엔 GrabCut이 아예 아닌 방법으로도 확인됨.

**고친 것 (1) -- 소형 요소는 실제 손그린 칼선 모양을 그대로 사용**: `core/interactive_cutline.py`에
`generate_cutline_from_known_silhouette()` 추가. 이 파일은 "새 그림"이 아니라 "이미 칼선이 있던 시트를
다시 그리는" 작업이라서, 문제의 두 요소를 포함한 12개 전부 이미 실제 손그린 칼선 폴리곤이 파일 안에
있음(`tile0_elems_px`) -- 픽셀로 재검출이 안 되는 이 두 요소만, 그 실제 폴리곤을 다시 세그멘테이션하는
대신 모서리만 살짝 다듬어서(왕복 버퍼, 순 크기 변화 없음) 그대로 새 칼선으로 사용. 토끼 액자 도무송
때 이미 썼던 것과 같은 원칙(재검출 불가능이 확인된 경우, 이미 검증된 실제 경계를 그대로 신뢰) --
`generate_cutline_auto`의 `small_element_max_dim_mm` 분기에 `reference_silhouette_px` 파라미터를
새로 연결, 참조 칼선이 없을 때만 기존 `_rect_trim_cutline`(사각형)으로 대체(임시값 표시 포함).

**고친 것 (2) -- 서로 다른 요소 간 2mm 최소 간격을 표준 규칙으로 격상**: 이번 라운드 전까지는 타일 안
12개 요소의 칼선을 전부 따로따로 생성한 뒤 7개 배치에 복제하고 마지막에 `union_all()`로 합치기만
했음 -- 서로 다른 요소끼리 얼마나 가까운지는 한 번도 검사한 적이 없었음(문제였던 소품 네모 칼선이 옆
캐릭터 칼선과 겹친 게 바로 이 때문). `core/cutline_core.py`에 `merge_close_elements()` 추가 --
`compute_offsets`가 한 도안 내부의 떨어진 조각들을 합칠 때 이미 쓰던 "간격의 절반만큼 바깥으로
버퍼 → 다시 안으로 버퍼" 트릭을, 완전히 독립적인 여러 요소들의 칼선 전체(unary union)에 그대로 적용한
것. 복제·배치까지 끝난 최종 전체 시트 위에서 딱 한 번만 실행하도록 배치 -- 이러면 같은 타일 안 이웃과
타일 반복 경계에서 가까워지는 경우를 한 번에 다 잡을 수 있음.

**재확인**: 85개(12x7+토끼1) → 2mm 간격 강제 후 78개. 어느 쌍이 합쳐졌는지 실제로 추적해봄
(`generated_tile_cutlines_px[i].distance(...)` 전수 비교) -- 타일 안 5번(큰 잠자는 햄스터 몸통)과
6번(산타모자 햄스터) 요소가 실제로 10.9px(≈0.9mm)밖에 안 떨어져 있어서 병합됐고, 이게 7개 타일
배치 전부에서 똑같이 일어나 78개(85-7)가 정확히 설명됨 -- 문제였던 소품(2,4,7,8,11번)들은 전부
독자적인 자기 모양 그대로 닫힌 도형으로 남아있고, 옆 캐릭터와 겹치지도 않음(겹침 렌더링으로 직접
확인: `scratch/v6_crop_elem2/4/7/8/11.png`, 병합된 5-6번 쌍도 `scratch/v6_crop_elem5_6.png`로
확인 -- 두 캐릭터가 실제로 맞닿을 만큼 가까워서 파란 선이 그 사이를 자연스럽게 하나로 잇고 있음, 이상한
장거리 오합침이 전혀 아님). 전체 페이지 렌더(`scratch/v6_full_page.png`)로 6장 타일+회전 배치+토끼
액자까지 전부 육안 확인.

**전달**: 최종 사본(`5조수희_5_유포지_인델별(색감 수정)_v6.ai`)과 비교 이미지 8장은 대화창/작가님
컴퓨터(Desktop, `v6_비교` 폴더)로 바이트 검증 후 전달. 저장소에는 `core/cutline_core.py`
(`merge_close_elements`)와 `core/interactive_cutline.py`(`generate_cutline_from_known_silhouette`,
`reference_silhouette_px` 파라미터) 커밋.

## 열여섯 번째 업데이트 — 도구 자체의 안전장치 4건 + GUI 시트 합성 연결 (2026-08-26)

**요청 배경 (그대로, 4가지)**:
1. "도안을 슬롯에 맞춰 몰래 축소하지 않는다."
2. "이미지가 훨씬 커지면 업샘플 배율을 자동으로 낮추는 것"
3. "UI에 '정밀도' 같은 이름으로 옵션 노출"
4. "칼선이 도안에 너무 가깝게 잡히면, 실제 인쇄/커팅 과정에서 미세하게 밀리는 것만으로도 칼선이 도안을
   잘라먹을 수 있다는 실무 피드백. 오프셋 값을 세이프티/칼선/블리딩 각각 자유롭게 입력할 수 있게 해뒀던
   게, 값을 너무 작게(또는 0으로) 넣어도 그대로 통과되는 게 문제였음."

이어서 "가이드 파일 + 도안 여러 장을 한 번에 넣고 시트 전체 미리보기를 볼 수 있게 만드는 것(지금은
스크립트 레벨까지만 구현)" 요청과 "모두 반영해"로 다섯 가지 전부를 이번 라운드에서 처리.

이번 항목은 특정 실제 파일 재작업이 아니라 도구 자체의 일반 동작을 고치는 것이라 실제 클라이언트 파일이
필요 없었고, 검증은 전부 이미 저장소에 공개로 커밋돼 있던 데모 픽스처(`samples/ring.png`,
`samples/scene.png`, `samples/guide_demo.pdf` 등)로만 진행 -- 새 합성 이미지를 만든 게 아니라 이미
있던 공개 데모 자산을 그대로 재사용.

**1) 슬롯 자동 축소 기본값 다시 되돌림** (`core/sheet_layout.py`): 네 번째 업데이트에서 실무 편의를
위해 `auto_fit=True`를 기본값으로 바꿨었는데, 이번 피드백으로 그게 틀렸다는 걸 재확인 -- 슬롯보다 큰
실제 마스터 도안이 조용히 줄어드는 건 인쇄 품질 문제로 이어질 수 있는 변경이라 절대 몰래 일어나면 안
됨. `auto_fit` 기본값을 다시 `False`로 되돌려서 기본은 위반만 보고(2026-08-25 이전 동작으로 복귀)하고,
그래도 자동 축소를 쓰고 싶을 때를 위해 `SlotPlacement`에 `resize_note` 필드를 새로 추가 -- 실제로
축소가 일어나면 전/후 크기(mm)와 축소 비율을 항상 기록해서, 켜서 쓰는 경우에도 "성공"과 "축소됨"이
분리되지 않고 항상 같이 보이게 함. 공개 데모(`samples/guide_demo.pdf` 슬롯 35.7×37.4mm +
`samples/scene.png` 65.2×26.5mm 콘텐츠)로 기본값은 위반만 보고, `auto_fit=True`로는 33.7×13.7mm(52%)로
축소되고 그 사실이 그대로 보고되는 것을 직접 실행해 확인.

**2) 업샘플 배율(정밀도) 자동 조정** (`core/cutline_core.py`): 서브픽셀 컨투어 추출은 이미지를
`supersample`배 확대해서 처리하므로 비용이 배율의 제곱 x 원본 해상도에 비례해 커짐. `auto_supersample()`
신규 추가 -- 업샘플된 캔버스의 긴 변이 상한(`DEFAULT_MAX_UPSAMPLED_DIM`)을 넘지 않도록 배율을 1까지
자동으로 낮춤. 상한값은 지금까지 실제로 처리한 파일들(4495×3074, 4491×3084 등, 전부 4500px대)이 기본
4배 정밀도를 그대로 유지하도록 여유 있게(20000) 잡아서, "이미지가 훨씬 커지면"이라는 말 그대로 일상적인
실제 파일은 전혀 영향받지 않고 그보다 훨씬 큰 원본만 자동으로 낮아짐 -- 직접 계산해 확인: 1772x945(이번
프로젝트가 다룬 타일 크기) 4배 유지, 4495x3074(실제 납품 파일 크기) 4배 유지, 6000x6000은 3배로,
12000x8000/50000x50000은 1배로 자동 조정됨. `load_raster_design`/`segment_design_in_region`/
`load_vector_design`에 `note_sink` 파라미터를 추가해서, 자동으로 낮아졌을 때 그 사실을 호출하는 쪽이
받아볼 수 있게 함(조용한 변경이 아님).

**3) GUI에 "정밀도" 옵션 노출**: `gui/app.py`의 "2. 작업 해상도" 아래에 정밀도(업샘플) 드롭다운(1~4배,
기본 4배) 추가. 이 값은 위 자동 조정의 "요청 상한"으로 쓰이고, 실제로 자동으로 낮아지면 칼선 생성 완료
메시지에 그대로 표시됨.

**4) 오프셋/여백에 안전 최소값 강제 -- 자유 입력 값도 너무 작으면(또는 0이면) 그대로 통과되지 않음**:
세이프티/칼선/블리딩 다단계 경로(`OffsetSpec.enforce_minimum_gap()`, `MIN_GAP_MM=2.0mm`)는 이미
보호돼 있었지만, 선화/무테 단일 간격 경로(`core/image_style.py`의 `generate_style_cutline`)에는 그런
보호가 아예 없어서 0이나 그에 가까운 값이 그대로 쓰이고 있었음(실제 GUI의 "선화/무테 간격" 입력창이
자유 텍스트라 스핀박스 최소값 없이 직접 0을 타이핑해서 넣을 수 있었음). 다만 여기에 다단계 경로와 같은
2.0mm를 그대로 재사용하면, 이 프로젝트가 이미 실측으로 검증해둔 정당한 실무 여백(1.0~1.7mm대, 심지어
라벨류는 0.55~0.72mm)까지 매번 조용히 2.0mm로 올려버리는 부작용이 생김 -- 그래서 별도의, 더 좁은
`MIN_STYLE_MARGIN_MM = 0.5mm`를 새로 도입(이 프로젝트가 실제 파일들에서 측정한 가장 좁은 정당한 여백
기준에서 산출). `generate_style_cutline`에 `note_sink` 파라미터를 추가해 이 값 미만이 입력되면 자동으로
올리고 그 사실을 기록, `generate_cutline_by_style`/`generate_cutline_auto`도 이 기록을 `adjustments`에
그대로 실어 나르도록 연결(그동안 `generate_cutline_by_style`가 `adjustments=[]`로 항상 비워뒀던 것도
같이 고쳐짐). GUI도 이 경로일 때는 (다단계 경로의 세이프티/칼선/블리딩이 아니라) "선화/무테 간격"
스핀박스 쪽으로 조정된 값을 반영하도록 분기 추가. 공개 데모(`samples/ring.png`)로 margin=0mm 입력 시
"0.5mm로 자동 조정" 메시지와 함께 정상적으로 선이 생성되고, margin=1.5mm처럼 이미 안전한 값은 아무
메시지 없이 그대로 통과되는 것을 직접 실행해 확인.

**5) "가이드 + 여러 도안" GUI 연결**: `gui/app.py`에 "0. (선택) 가이드 + 여러 도안 → 시트 합성" 섹션
추가 -- 가이드 파일 선택, 도안 여러 장 선택(다중 파일 다이얼로그), 자동 축소 체크박스(기본 꺼짐, 위
1번과 일관되게)/여백 mm, "시트 합성 미리보기" 버튼. `core/guide.load_guide_from_ai` +
`core/sheet_layout.place_designs_into_sheet`로 합성한 결과 PNG가 그대로 "1. 도안 파일" 입력으로
채워져서, 이후 오프셋/스타일/칼선 종류/생성/내보내기는 파일 하나만 작업할 때와 완전히 동일한 코드
경로를 그대로 탐 -- `core/cutline_core.generate_cutlines`가 이미 한 이미지 위의 여러 개별 도형을
처리할 수 있으므로 새 파이프라인이 필요 없었음(다섯 번째 업데이트 때부터 있던 설계 그대로).

## 열일곱 번째 업데이트 — 작업 종류(완칼/스티커/도무송) 재정립 + 누적 방식으로 전환, 선화→유테 개명 (2026-08-26)

**요청 (직접 인용)**: "칼선 작업의 기본 원리 도안 하나에 외곽선 하나를 그 이미지의 실제 옵션(모양)에
맞춰 만드는 것 / 칼선 기준을 정하자. 타입도 선화, 무테 중 선택하게 해. 이미지 단독 하나의 칼선을
만들면 완칼, 도안 안에서 요소의 칼선을 만들면 스티커, 그 중 여백에 다른 이미지를 추가해 도무송(사각형,
정원, 타원형, 정사각, 완칼) 제작하는 것을 확인 후 선택지를 주고 작업을 하는게 기본 시스템 원리로,
드래그 하고 해당 옵션명을 선택해 각각의 칼선이 하나의 파일에 동시 적용 되는 원리로 작업 / 유테:테두리
외곽선이 있는 이미지 / 무테:테두리 외곽선이 없는 이미지 / 단순하고 명료하게 정립". 이어서 두 가지를
직접 확인받음 — 도무송 흐름: "스티커를 한 판에 모아서 규격에 맞게 직사각, 정사각 형태의 씰스티커를
배열하고 남은 여백에 토끼 그림같은 도무송 스티커 작업을 하는거야." / 여러 선택이 한 파일에 합쳐지는
방식: "여러 번 드래그 + 옵션 선택 → 전부 한 파일에 누적."

**1) "선화" → "유테"로 개명**: `core/image_style.py`의 `ImageStyle.LINE_ART`의 `.value`를 "선화"에서
"유테"로 바꿈(멤버 이름 `LINE_ART`와 내부 로직은 그대로 -- 화면에 보이는 이름만 바뀜). 이유는 "유테
(테두리 외곽선 있음)/무테(테두리 외곽선 없음)"가 서로 반대말로 바로 짝지어지는 이름이라 "선화/무테"보다
더 단순하고 명료하기 때문(작가님 표현 그대로 "단순하고 명료하게 정립"). `core/image_style.py`,
`core/interactive_cutline.py`, `core/style_classify.py`, `inspect_cutline_margins.py`, `README.md`의
관련 주석/문서/실행 시 표시 문구를 전부 같이 바꿈(기계적 문자열 치환 후 직접 grep으로 잔여 "선화"
없음을 확인). 과거 날짜의 일지 기록(이 파일의 이전 항목들)은 그 시점의 실제 대화 기록이므로 그대로 둠.

**2) 작업 종류(완칼/스티커/도무송) 세 갈래 재정립**: 이미 존재하던 두 축 -- 이미지 종류(자동 감지/유테/
무테/직접 설정, `core/image_style.py`)와 칼선 종류(완칼 + 도무송 4종, `core/cutline_types.py`) -- 를
그대로 재사용하되, 그 위에 "지금 만들려는 게 무엇을 가리키는 칼선인가"를 먼저 고르는 `job_type`
한 겹을 추가함(`gui/app.py`의 `self.job_type`: FULL_CUT/STICKER/DOMUSONG). **완칼**은 이미지 전체(또는
선택한 요소 하나)의 실제 실루엣을 그대로 트레이싱(선택이 없으면 전체 이미지에 `generate_cutlines`,
있으면 그 영역에 `generate_cutline_for_selection(cutline_type=FULL_CUT)`). **스티커**는 도안 안에서
드래그로 고른 요소 하나에 대해 기존 자동 감지/유테/무테 로직(`generate_cutline_auto`/
`generate_cutline_by_style`)을 그대로 적용. **도무송**은 선택 영역에 대해 기존 5종 도형 선택
(`generate_cutline_for_selection` + `CutlineType`)을 그대로 적용 -- 이 5종(사각형/정사각형/타원형/
정원형/완칼)이 작가님이 언급한 "도무송(사각형, 정원, 타원형, 정사각, 완칼)"과 이름만 다르고 이미
정확히 일치하는 것을 코드에서 다시 확인함(새로 만들 필요 없음). `gui/app.py`의 UI를 완칼/스티커/도무송
라디오 버튼 한 그룹 + 그 아래 조건부로 의미가 있는 오프셋(4번)/스티커 세부(5번)/도무송 세부(6번)
섹션으로 재배치, 안내 문구도 실제 동작에 맞게 다시 씀.

**3) 누적(accumulation) 워크플로우로 전환 -- 신규 `core/accumulate.py`**: 지금까지는 "칼선 생성"을
누를 때마다 직전 결과를 통째로 대체하는 1회성 방식이었음. 이걸 작가님이 확인해준 실제 작업 방식대로
바꿈 -- 드래그 → 작업 종류/세부 옵션 선택 → "이 영역 추가 + 미리보기"를 누르면 그 결과가
`self._accumulated` 리스트에 쌓이고, 매번 그 전부를 새 `core/accumulate.py`의 `combine_results()`로
합쳐서 화면에 보여줌. `combine_results()`는 (a) 각 항목의 `design`(원본 도안 참조용)을 전부 union,
(b) 항목마다 다른 `offsets` 티어 구성(완칼/도무송은 safety+cut+bleed 3단, 스티커는 cut 1단만)을
실제로 존재하는 티어 이름 기준으로 각각 union, (c) 합쳐진 각 티어에 `core/cutline_core.py`의
`merge_close_elements`(`MIN_GAP_MM=2.0mm`)를 다시 한 번 적용 -- 이미 확립된 "서로 다른 요소끼리 2mm
미만이면 병합"이라는 최우선 규칙(열다섯 번째 업데이트)을, 이제는 "같은 파일 안의 서로 다른 작업 종류"
사이에도 그대로 적용한 것. `gui/app.py`에 "이 영역 추가 + 미리보기"(기존 "칼선 생성/미리보기" 버튼을
누적 의미로 재정의)와 "누적 초기화" 버튼, 누적 개수 표시 라벨을 추가. 새 파일을 열거나(`_choose_file`)
새 시트를 합성하면(`_on_sheet_built`) 이전 파일의 누적 항목은 자동으로 폐기(다른 이미지 좌표계의
칼선이 섞이면 안 되므로).

**검증**: 실제 클라이언트 파일이 아닌, 이미 저장소에 있던 공개 데모 픽스처(`samples/ring.png`,
`samples/scene.png`)만 사용해 `test_accumulate.py`를 작성 -- Tkinter가 이 세션의 기본
파이썬(3.11)에는 없어서 `python3.12`(시스템에 `python3-tk` 설치됨) + `xvfb-run`(가상 디스플레이)으로
실제 `gui.app.CutLineApp` 클래스를 그대로 띄워서 헤드리스로 구동. scene.png의 실제 도형 3개(각각
`load_raster_design`으로 미리 측정한 실제 bbox 기준 선택 영역)에 완칼/스티커-유테/스티커-무테/
도무송-정원형을 하나씩 적용해 각 항목의 `offsets` 티어 구성이 기대대로임을 확인(완칼·도무송은
safety/cut/bleed 3단, 스티커는 cut 1단), `ImageStyle.LINE_ART.value == "유테"`도 같은 스크립트에서
직접 확인. 세 항목을 `combine_results`로 합친 뒤: 합쳐진 결과의 티어 구성이 올바름, 서로 다른 작업
종류로 만든 폴리곤끼리도 실제 거리 계산(`Polygon.distance`)으로 최소 2mm(px 환산) 이상 떨어져 있음을
확인, `export_svg`/`render_preview`에 그대로 통과시켜 정상적으로 파일이 만들어짐을 확인, 미리보기
이미지를 직접 열어 육안으로도 재확인(분홍 자유형 완칼 실루엣 + 파란 사각 스티커 두 칸 + 주황 링을
감싸는 3중 원형 도무송이 한 이미지 안에 동시에 나타남). 필수 선택 누락 시 스티커/도무송 둘 다
`ValueError`가 정상적으로 발생하는 것도 확인. 기존 회귀 테스트(`test_pipeline.py`, `test_vector.py`,
`test_risk.py`, `test_fidelity.py`, `test_sheet_demo.py`, `test_sheet.py`)도 전부 재실행해 기존과
동일하게 통과함을 확인 -- 이번 변경은 GUI/누적 로직에 새 계층을 얹은 것이라 core의 기존 단일-경로
함수들은 시그니처/동작을 전혀 바꾸지 않았음.

(`core/image_style.py`, `core/interactive_cutline.py`, `core/style_classify.py`,

확인 질문을 드림 -- "네가 제출한 예시 파일이야. 결론은 칼선 이탈과 중첩이니까 해결해"라는 답을 받고
직접 그림을 다시 뜯어봄.

**원인**: 도무송/완칼의 3겹 동심원(세이프티/칼선/블리딩) 자체는 처음부터 있던 정상 동작이었지만, 무테
(BORDERLESS) 항목에서 실제로 진짜 문제를 발견함 -- 그 항목의 테스트용 드래그 선택 영역에 15px의
padding만 줬는데, 당시 dpi 설정(GUI 기본값 300, 정작 이 데모 이미지들의 원래 관례는 150)에서
margin_mm=1.5mm를 안쪽으로 미는 거리가 약 17.7px이었음 -- 즉 선택 영역 자체가 안쪽으로 미는 거리보다도
좁아서, 계산된 무테 칼선이 실제 그림(파란 물방울 도형)의 오른쪽 끝보다 더 안쪽으로 들어가 있었음(실제
그림을 칼선이 침범). 이건 테스트 스크립트만의 문제가 아니라, 실제 GUI에서도 작가가 무테 선택을 그림
가장자리에 비해 너무 타이트하게 드래그하면 똑같이 일어날 수 있는, 지금까지 아무도 검사하지 않고
있었던 진짜 위험 요소였음(무테는 원래 "선택 영역 자체를 안쪽으로 줄인다"는 정의라 실제 내용물을 보지
않기 때문에, 이 실패 유형은 기존의 MIN_GAP_MM/MIN_STYLE_MARGIN_MM 같은 "여백 숫자가 너무 작다"는
보호로는 전혀 잡히지 않음 -- 여백 숫자 자체는 정상이어도 선택 영역이 그림에 비해 좁으면 여전히 뚫림).

**수정**: `core/image_style.py`에 `_measure_content_bbox_px()`를 새로 추가 -- 무테는 원래 전체
GrabCut 세그멘테이션을 하지 않는 게 정의이므로, 그와 어울리게 가벼운 방식으로만 확인함(알파 채널이
실제로 쓰이면 알파 기준, 아니면 크롭 네 귀퉁이 색과의 거리 기준)으로 선택 영역 안의 실제 내용물
경계만 측정. `generate_style_cutline`의 BORDERLESS 분기에서, 계산된 칼선의 경계가 이 실제 내용물
경계보다 안쪽으로 들어가면 몇 mm나 침범하는지 계산해 `note_sink`에 경고를 남김(기존 "조용한 변경 없음"
원칙 그대로). **자동으로 선택 영역을 넓히지는 않음** -- 무테 선택 영역은 실제로 (가이드에서 온 슬롯/칸
사각형처럼) 그림보다 일부러 넉넉하게 잡힌 정당한 경우도 있어서, 도구가 마음대로 그 크기를 바꾸는 건
다른 부작용을 만들 수 있음. 대신 작가가 다시 드래그하거나 간격을 줄이도록 안내만 함(경고, 자동 보정
아님 -- 다른 안전장치들과 성격이 다름을 의도적으로 구분).

**검증**: `test_accumulate.py`를 dpi=150(이 데모 이미지들의 원래 관례)으로 명시하고, 무테 항목의
padding을 20px(margin 대비 충분)로 바로잡아 더 이상 경고가 뜨지 않는 것을 확인. 같은 도형으로 일부러
padding을 3px까지 좁힌 별도 케이스를 추가해, 새 안전 검사가 정확히 경고를 남기는 것도 확인(회귀
테스트). 수정된 미리보기 이미지를 다시 렌더링해 육안으로 재확인 -- 파란 물방울 도형 주변 사각형 칼선이
이제 실제 그림 가장자리 바깥쪽에 여유를 두고 그려짐(더 이상 그림 끝을 스치거나 침범하지 않음). 기존
회귀 테스트(`test_pipeline.py`, `test_vector.py`, `test_risk.py`, `test_fidelity.py`,
`test_sheet_demo.py`, `test_sheet.py`) 전부 재실행해 통과 확인.

**전달**: 전부 일반 코드/문서 변경(실제 클라이언트 파일과 무관) -- 저장소에 코드(`core/image_style.py`,
`test_accumulate.py`) + `README.md` + 이 일지 그대로 커밋.

## 열아홉 번째 업데이트 — GUI 디자인 전면 개편: 버튼 잘림 구조적 해결 + customtkinter로 시각 언어 새로 그림 (2026-08-26, 같은 날)

**계기**: 실제로 프로그램을 설치해서 써 보신 뒤 직접 남겨주신 피드백 -- "ui 디자인이 너무 구리고
버튼 위치도 한쪽에 몰려서 화면에서 짤려, 그러니까 피그마에서 최신 트렌드 찾아서 공부해서 버튼 위치와
폰트 그리고 디자인 다 갈아 엎어", 곧이어 "무조건 세련되고 고급지게"라는 확고한 추가 지시.

**원인**: 열일곱 번째 업데이트에서 작업 종류(완칼/스티커/도무송)를 세 갈래로 재정립하면서 왼쪽 조작
패널의 섹션이 8개(가이드+시트 합성/도안 파일/작업 해상도/작업 종류/오프셋 간격/스티커 세부/도무송
세부/누적)로 늘었는데, 기존 `tkinter`/`ttk` 레이아웃은 이 모든 섹션을 고정 높이 `ttk.Frame`에 세로로
그냥 쌓기만 하고 스크롤 수단이 전혀 없었음 -- 그래서 창 높이가 조금만 작아도(또는 섹션이 늘어난
지금은 기본 창 크기에서도) 맨 아래의 "SVG로 내보내기" 같은 버튼이 화면 밖으로 밀려 아예 보이지도,
눌리지도 않는 상태가 됐음. 색상/폰트도 순수 시스템 기본 `ttk` 테마 그대로라 각 섹션의 위계(핵심 동작과
부가 옵션의 구분)가 시각적으로 전혀 드러나지 않았음.

**수정**: GUI 툴킷을 `tkinter`/`ttk`에서 `customtkinter`(현대적 플랫 디자인의 tkinter 래퍼)로 전면
교체. (1) **잘림 문제의 구조적 해결** -- 왼쪽 조작 패널 전체를 `CTkScrollableFrame`으로 감쌈. 이제
섹션이 몇 개든, 창을 얼마나 작게 줄이든 스크롤바가 항상 나타나 모든 버튼에 닿을 수 있음(문제 자체가
"버튼이 화면보다 커지지 않게 계속 줄여야 하는" 임시방편이 아니라 구조적으로 사라짐). (2) **시각 언어
재설계** -- 단일 브랜드 컬러(인디고 `#4338CA`)를 기준으로 카드형 섹션(둥근 모서리 14px + 옅은 테두리
`#E7E7EB`, 배경 `#FFFFFF` 카드가 연회색 `#F6F6F8` 배경 위에 뜬 구조), 명확한 1차(강조 채움, "이 영역
추가 + 미리보기"/"SVG로 내보내기")/2차(아웃라인, 나머지 전부) 버튼 위계, 통일된 타이포그래피(맑은
고딕, 제목 21/섹션 14/본문 13/설명 11)로 새로 그림. 세이프티(초록)/칼선(빨강)/블리딩(파랑) 색상
스와치처럼 이미 실무적으로 의미가 있는 신호는 그대로 유지하되 톤만 다듬음(`#16A44A`/`#DC2626`/
`#2563EB`). 기존 `ttk.Spinbox`들은 모두 라벨 + `[-][입력칸][+]` 스테퍼 + 단위로 통일한 새 도우미
`_make_number_field()`로 교체(`_offset_row`는 제거). `정밀도(업샘플)` 콤보박스는 `self.precision`이
계속 `IntVar`로 남을 수 있도록 문자열 `StringVar` 프록시를 하나 두고 선택 시 `int()`로 변환해 반영.
(3) **로직은 전혀 건드리지 않음** -- `__init__`의 모든 상태 변수 이름/타입, `_generate_one_item`/
`_run_generate`/`_validate_inputs`/`_choose_file`/드래그 선택 핸들러 등 모든 비즈니스 로직 메서드는
그대로 두고, `_build_layout`과 위젯을 만드는 부분만 다시 씀(버튼 비활성화는 `.config(state=...)`가
아니라 customtkinter 위젯에 안전한 `.configure(state=...)`로 통일).

**검증**: 먼저 `xvfb-run -a python3.12 test_accumulate.py`로 실제 `gui.app.CutLineApp` 클래스를
헤드리스로 구동해 완칼/스티커(유테/무테)/도무송 각 항목 생성, 누적, 최소 간격, 내보내기/미리보기,

지점(작업 종류/오프셋/스티커 세부 옵션)과 맨 아래(도무송 세부/누적/버튼들)까지 각각 캡처해 직접 눈으로

회색조로 비활성 표시되는 것도 확인. 마지막으로 기존 회귀 테스트 전부(`test_pipeline.py`,

## 스무 번째 업데이트 — 디자인 세부 조정 + 주 입력 파일을 어도비 일러스트로 + 첫 실행 튜토리얼 (2026-08-26, 같은 날)

**계기**: 열아홉 번째 업데이트로 전달한 GUI 개편을 보신 뒤 바로 이어서 주신 구체적인 다섯 가지 추가
요청 -- "화면이 너무 크고 글자가 작아 폰트 0.8 포인트 키우고 파일은 칼선을 넣을 어도비 일러스트 파일과
png,jpg 세가지 선택지로 만들고 버튼도 더 라운딩 넣고 크기 10mm 키워, 그리고 주 입력 파일은 어도비
일러스트야. 설치 후 첫 화면에 튜토리얼을 자동으로 뛰우고 아래 선택 칸을 넣어서 다시 보지 않기도
추가해. 화면비율도 1:2로 맞춰".

**"화면비율 1:2"를 먼저 확인함**: 지금 구조(왼쪽 조작 패널 + 오른쪽 미리보기가 나란히 있는 형태)에서
이 비율을 창 전체에 적용할지, 두 패널 폭 비율에 적용할지, 세로로 길게(1:2) 갈지 가로로 넓게(2:1) 갈지에
따라 결과물이 완전히 달라져서, 임의로 정하는 대신 선택지 4개를 만들어 여쭤봄 -- "창 전체가 가로로 넓은
1:2(세로:가로, 즉 2:1)"로 확정.

**반영 내용**:
1. **폰트 +0.8pt**: `gui/app.py`에 `FONT_SIZE_BUMP = 0.8`과 `_bumped(size)` 헬퍼를 추가, 기존 5개
   `CTkFont` 크기(제목21/섹션14/본문13/설명11/버튼13) 전부에 적용 후 반올림(tkinter 폰트 크기는 정수만
   허용).
2. **창 크기/비율**: 확정된 "가로 2:1"에 맞춰 기존 1180×800(비율 약 1.48:1, "너무 크다"는 지적대로)을
   1000×500(정확히 2:1)으로 축소. 좌/우 나란히 배치 구조는 그대로 유지(스크롤 패널 덕분에 세로 공간이
   줄어도 잘리는 요소는 없음).
3. **버튼 라운딩 + 크기 10mm**: 일반 모니터 기준(96dpi)으로 10mm ≈ 37.8px 환산(`BUTTON_SIZE_BUMP_PX`),
   1차/2차 버튼(`_btn_primary`/`_btn_secondary`) 높이에 그대로 더하고 `corner_radius`도 10→24/20으로
   키움. +/- 스텝퍼처럼 옆의 입력창과 비례를 맞춰야 하는 작은 보조 컨트롤은 더 작은 폭(26→30px,
   radius 6→10)으로만 키워 비율이 깨지지 않게 함. 입력창/콤보박스도 톤을 맞춰 radius를 살짝 키움(8→12).
4. **파일 형식 3종 + 주 입력 파일 = 어도비 일러스트**: "1. 도안 파일" 선택창을 어도비 일러스트(.ai,
   맨 앞 기본 필터)/PNG/JPG로 좁힘. 신규 `core/ai_import.py`의 `load_ai_as_raster()`가 -- 이 프로젝트가
   이미 검증한 실제 완성 파일들의 구조(심겨 있는 하나의 플랫 인쇄용 래스터)를 그대로 이용해 -- .ai 파일
   안에 이미 심겨 있는 실제 인쇄용 이미지를 원본 해상도 그대로 추출(다시 렌더링해서 화질을 잃지 않음).
   심겨 있는 이미지가 아예 없는 순수 벡터 파일이면 지정한 DPI로 페이지 자체를 래스터화하는 것으로 자동
   대체. 추출/변환된 결과는 기존 시트 합성 결과가 그랬듯 `self.input_path`에 내부 작업용 PNG 경로로
   들어가고, 이후 GrabCut/드래그 선택/누적 파이프라인은 PNG를 직접 연 것과 완전히 동일하게 그대로 탐 --
   새 코드 경로를 추가한 게 아니라 이미 검증된 raster 파이프라인 앞에 새 "입구"만 하나 만든 것. 다만
   내보내기 기본 파일명이 이 내부 임시 경로를 따라가면 "_ai_source_raster_cutlines.svg"처럼 이상해지는

## 스물두 번째 업데이트 — 개인/기업 라이선스 시스템: 기기 제한, 원격 잠금, 재활성화 키 (2026-08-26, 같은 날)

**검증**: (1) 헤드리스 스크립트(`test_license.py`)로 로컬 테스트 서버에 대해: 개인 라이선스 2대 활성화
