꽃잎 장식이 셀 위/아래/옆 가장자리까지 흩어져 채워진 시트에서는, 추적이 그 장식 하나하나의 색 경계를
따라가며 위아래로 지그재그로 이어붙인 지저분한 칼선을 만들고 있었음.

원인은 이 프로젝트가 처음부터(7번째/9번째 업데이트) 검증해둔 무테의 원래 정의 그대로였음 -- 무테는
"여러 요소를 서로 배경 여유를 두고 그룹으로 묶어야 하는 경우"(이번 추적 기능이 원래 만들어진 이유)와
"배경까지 통째로 채우는 연속 무늬라 애초에 추적할 대상이 없는 경우"(원래부터 사각형 축소로 처리하던
경우, 예: 실제파일 중 하나였던 "연속 배경 패턴형" 시트) 두 가지를 모두 포함하는데, "우선 모든 무테에
적용해봐"로 추적을 무조건 켜면서 후자의 경우까지 억지로 추적하게 된 것이 문제였음.

**수정**: `core/image_style.py`에 두 경우를 가르는 판정을 추가함 -- 추적된 모양이 선택 영역(셀) 사방 중
단 한 면이라도 가장자리에 거의 닿아 있으면(실제 배경 여유가 없음) "배경까지 채우는 연속 무늬"로 보고
추적 결과를 버리고 예전처럼 사각형 자체를 안쪽으로 줄인다. 반대로 사방 전부에 실제 여유(halo)가 있으면
"여러 요소를 그룹으로 묶어야 하는 경우"로 보고 그대로 추적+묶기+축소를 적용한다. 이 판정은
`core/style_classify.py`가 유테/무테를 자동 구분할 때 이미 실전에서 검증해 쓰고 있던 "할로 우선 판정"과
완전히 같은 원리(같은 임계값)를 재사용한 것 -- 새 방식을 발명한 게 아니라, 이미 검증된 규칙을 같은
자리에 다시 적용한 것.

**검증**: 합성 도형(알려진 기하 구조, 알고리즘 동작 확인 목적)으로 "장식이 셀 가장자리까지 흩어진 경우"를
재현해 새 판정이 정확히 사각형 축소로 되돌아가는 것과, 기존 "서로 떨어진 두 요소가 진짜 배경 여유를 두고
있는 경우"는 그대로 추적 경로를 타는 것을 `test_borderless_silhouette.py`에 새 테스트로 추가해 확인.
`test_accumulate.py`의 "빠듯한 선택" 케이스도 다시 살펴봄 -- 3px처럼 이 프로젝트의 엣지 검출 자체가 갖는
노이즈 폭(2px) 이하로 빠듯한 여유는 "진짜 halo"로 신뢰할 수 없어 다시 사각형 폴백 + 기존 경고가 뜨는 게
맞다는 것을 확인하고 테스트를 그에 맞게 다시 씀(이건 회귀가 아니라, 노이즈 수준의 여유를 함부로 믿지
않는 더 안전한 동작). 반면 노이즈 폭보다는 확실히 넓은(8px) 빠듯한 선택은 여전히 추적 경로를 타고
경고 없이 처리되는 것도 새로 확인함 -- 11번째 업데이트의 개선 효과가 진짜로 필요한 경우에는 그대로
남아있음. 전체 회귀 테스트 재실행해 전부 통과 확인.

## 스물네 번째 업데이트 — "교재" 폴더의 실제 참고 파일들로 여백/간격 기본값 재검증

**요청 (그대로)**: "바탕화면의 컷라인 스튜디오 안 폴더 교재에 있는 모든 칼선 유형과 거리감, 여백을
학습하고 적용해." 바탕화면의 `컷라인 스튜디오 샘플/교재` 폴더에는 마스킹테이프/리무버블 스티커/
도무송·폼파일/씰스티커 가이드 등 여러 유형의 실제 완성 참고 파일이 모여 있었음.

**방법**: 이미 있는 진단 도구(`inspect_cutline_margins.py`, `core/margin_inspector.py`,
`core/guide.py`)로 그 폴더의 실제 파일 8개(마스킹테이프 예시 3개, 지난 일지에 아직 없던 새 리무버블
스티커 실물 예시 2개, 씰스티커 가이드/도무송 폼파일 예시 3개)를 스크래치 폴더에서만 열어 실제 여백/
간격 수치를 측정하고, 측정이 끝난 즉시 전부 삭제(레포 안에는 어떤 원본도 복사·기록하지 않음, 이하
전부 실제 파일명 대신 "마스킹테이프 예시 A/B/C"처럼 임의로 붙인 이름으로만 기록).

**측정 결과 요약**:
- **마스킹테이프**: 이 파일들은 개별 모티프 칼선이 벡터 패스로 그려져 있지 않았음(물리적 다이/롤
  커터로 별도 처리되는 것으로 보임). 다만 벤더 템플릿 자체의 안전여백은 15mm 롤 기준 위/아래 각
  1.5mm로 두 예시 모두 동일 -- 기존에 이미 검증해 쓰고 있는 유테/무테 실무표준 1.5mm와 정확히 일치.
  예시 하나(마플샵 계열)는 개별 모티프 키스컷 개념 자체가 없는, 이미지를 겹쳐 이어붙이는 순수 연속
  패턴 구조였음 -- 이건 8월 26일에 멍푸님이 알려주신 "일반 마스킹 테이프는 재단이 필요 없어, 이미지를
  길게 이어가면 끝이야"라는 설명과 실제로 정확히 일치하는 실물 증거임(그날 여쭤봤던 "재단 없이 이어
  붙이기만 하는 기능을 따로 만들지" 질문이 아직 답을 못 들은 상태였는데, 이 실물로 그 케이스가 실제로
  존재함을 다시 확인함).
- **새 리무버블 스티커 실물 예시 2개**: `inspect_cutline_margins.py`로 정상 측정됨(단, 두 파일 다
  레이어 이름이 "칼선레이어"가 아니라 "칼선"이었음 -- 아래 수정 참고). 중앙값 0.6~1.7mm대로, 지금까지
  이미 확인해온 실무 범위(1.0~1.7mm)와 거의 일치 -- 현재 기본값 `DEFAULT_STYLE_MARGIN_MM=1.2mm`,
  최소값 `MIN_STYLE_MARGIN_MM=0.5mm`가 여전히 안전하고 적절함을 재확인.
- **도무송/폼파일 예시**: 실제 다이 21개 중 서로 가장 가까운 두 다이 사이 간격이 최소 2.34mm로,
  현재 강제하는 최소 간격 `MIN_GAP_MM=2.0mm`보다 살짝 더 넉넉했음 -- 즉 2.0mm는 여전히 안전한
  하한선이고(실제 업체 관행이 그보다 더 여유 있게 배치), 올릴 필요는 없음.

**결론 -- 숫자는 바꾸지 않음**: 이번에 새로 측정한 8개 실물 전부, 지금 코드에 이미 들어있는 기본값
(1.2mm/0.5mm/2.0mm/1.5mm)과 어긋나지 않았음 -- 오히려 그 값들이 실제로 여러 업체·파일에 걸쳐 안전한
근사값이라는 걸 다시 한번 실물로 확인해준 결과라서, 숫자 자체를 바꾸는 변경은 하지 않음.

**고친 것 -- 진단 도구의 작은 불편함**: 위 측정 중 실제로 겪은 문제 하나는 코드로 고쳤음.
`inspect_cutline_margins.py --layer`가 기본값으로 "칼선레이어"만 가정하고 있었는데, 방금 확인한 두 새
파일은 "칼선"이라는 다른(더 짧은) 이름을 쓰고 있어서 매번 손으로 `--layer 칼선`을 넣어줘야 했음. 이
스크립트는 사람이 직접 실행하는 진단용 CLI일 뿐 실시간 칼선 생성 파이프라인과는 무관(그 파이프라인은
작가의 실제 레이어 이름을 애초에 읽지 않음)이라 안전하게, 흔히 쓰이는 이름들("칼선레이어", "칼선",
"재단선", "cutline", "Cutline")을 `--layer`를 안 줬을 때 순서대로 자동으로 시도해보도록 고침 -- 전부
실패하면 시도한 이름 목록을 그대로 보여주는 오류로 남 (조용히 다른 레이어를 골랐다고 착각하게 두지
않음).

**검증**: 기존 `test_ai_cutline_reader.py` 재실행해 통과 확인(이 도구가 의존하는
`core/ai_cutline_reader.py`의 핵심 로직은 전혀 바꾸지 않음, CLI의 기본값 시도 순서만 바꿈). 공개 데모

정직하게 보여주는 오류로 정상 종료되는 것과, `--layer`를 직접 지정하면 그 이름 하나만 시도하는 기존
동작이 그대로 유지되는 것을 확인.

## 스물여섯 번째 업데이트 — "여전히 칼선이 엉망이야" 직접 검증 후 실제 버그 2건 수정

**요청 (그대로)**: "그럼 그것들을 모두 칼선 실험할 수 있게. 여전히 칼선이 엉망이야. 60초 이내에
학습한 데이터 기반으로 작업을 해. 너가 직접 프로그램을 사용해봐." 이어서 "추가로 모든 칼선은
매끄러워야하는데 지그 다 선이 구불구불해 이것도 중요하니까 반영."

**방법**: 화면 캡처만으로 추측하지 않고, 실제로 이미 이 대화방에 올라와 있던 실제 파일 하나(12칸
시트, 반복 패턴)를 스크래치 폴더에서만 열어, GUI가 "자동으로 여러 개 인식 + 추가"를 눌렀을 때
내부적으로 호출하는 것과 정확히 같은 코드(`core.ai_import.load_ai_as_raster` →
`core.ai_cutline_reader.load_real_grid_cells` → `core.interactive_cutline.generate_cutline_by_style`
→ `core.accumulate.combine_results` → `core.preview.render_preview`)를 제가 직접 순서대로
실행해 12칸 전체의 칼선을 만들어보고(총 17~26초, 요청하신 60초 이내), 그 결과 이미지를 직접
열어서 눈으로 확인 -- "학습한 데이터 기반"이라는 말씀대로, 작은 합성 이미지가 아니라 이 실제
파일로만 판단.

**찾은 문제 1 -- 작은 진짜 요소가 통째로 사라짐 (`core/segmentation.py`)**: 자동 인식된 칸 하나에
큰 캐릭터 하나 + 작게 그려진 요소들(말풍선, "●Rec" 아이콘, 네 귀퉁이 괄호 표시 / 다른 칸에서는
서류·음료 아이콘)이 같이 있을 때, 이 작은 요소들이 칼선 자체가 아예 안 생겼음 -- 실제 제작에
들어가면 그 부분이 통째로 잘려나가 없어짐. 원인: GrabCut 결과에서 "가장 큰 조각 대비 2% 미만이면
버린다"는 기존 규칙(원래는 큰 캐릭터 바로 옆에 붙어서 생기는 진짜 노이즈 티끌 하나를 지우려고 만든
규칙)이, 실측해보니 이 진짜 작은 요소들(592~8050px², 큰 캐릭터와 34~274px 떨어져 있어 전혀 안
붙어있음)까지 다 지워버리고 있었음. **고침**: "가장 큰 조각 대비 비율"이 아니라 "절대 크기가 노이즈
수준으로 작고(150px² 이하) *동시에* 다른 조각에 거의 붙어있음(5px 이내)"일 때만 버리도록 바꿈 --
실제 노이즈 사례(붙어있는 71px² 티끌)는 여전히 잡히고, 멀리 떨어진 작은 진짜 요소는 이제 전부
자기 칼선을 가짐. 이 12칸 파일로 재검증: 말풍선/아이콘/괄호/서류/음료 아이콘 전부 칼선이 생김.

**찾은 문제 2 -- 오프셋(margin) 단계에서 잔물결이 다시 살아남 (`core/image_style.py`,
`core/interactive_cutline.py`)**: 실제 캐릭터 실루엣을 margin_mm만큼 바깥으로 미는 단계에서, 그
전에 잔물결을 지우는 "close-then-open" 처리(presmooth)가 고정값(0.3mm)이라 실제로 쓰는
margin_mm(예: 1.2mm)보다 훨씬 작았음 -- presmooth 값을 0.3mm~1.6mm까지 여러 단계로 직접 바꿔가며
실제 파일로 확인한 결과, margin 자체보다 작은 presmooth는 margin을 미는 단계에서 되살아나는
잔물결을 못 막는다는 게 실측으로 확인됨. **고침**: presmooth를 margin_mm의 절반 이상은 항상
확보하도록(`max(2.0px, 0.3mm, margin_px*0.5)`) 바꿈 -- 유테(core/image_style.py)뿐 아니라 완칼/
도무송 경로(core/interactive_cutline.py의 `generate_cutline_for_selection`)에는 이 presmooth 단계가
원래 아예 없었던 것도 이번에 확인해서 같이 추가함(두 경로가 같은 GrabCut 결과를 쓰는데 한쪽만
매끄럽게 처리되고 있었음). 실제 파일로 재검증: 단순한 캐릭터(복슬복슬한 푸들 머리)는 눈에 보이는
잔물결이 사실상 사라짐. **다만 정직하게 남겨두는 한계**: 캐릭터 자체가 "귀 여러 개 + 사이 틈"처럼
진짜로 촘촘하게 굴곡진 실루엣일 때는, 그 굴곡 폭 자체가 margin 폭과 비슷하거나 좁아서, 아무리
presmooth를 키워도(margin의 2배까지 실험) 그 굴곡을 따라가는 선이 살짝 오르락내리락하는 건 남음
-- 이건 노이즈가 아니라 그 캐릭터의 실제 모양을 정확히 따라간 결과라, 더 지우려면 캐릭터의 진짜
디테일(귀 모양 등)을 뭉개야 함. 800% 같은 매우 높은 확대에서는 이 부분이 여전히 눈에 띌 수 있음 --
일반 확대에서는 눈에 띄게 나아짐.

**검증**: 회귀 테스트 22개 전부 재실행해 통과 확인(수정 전/후 동일). 이번 진단·검증에 쓴 실제 파일
사본과 중간 이미지는 전부 스크래치 폴더에서만 열어봤고, 확인 직후 전부 삭제(`rm -rf`) +
`git status --short`로 레포에 아무 것도 안 들어갔는지 재확인.

**전달**: 코드(`core/segmentation.py`, `core/image_style.py`, `core/interactive_cutline.py`) + 이
일지. 실제 파일이나 파일명은 코드/문서 어디에도 없음(전부 위처럼 일반적으로 서술).

**아직 열려 있는 것**: (1) 곰돌이 의상 캐릭터의 부드러운 털/그림자 halo 문제는 여전히 실제 파일을
못 받아 확인 대기 중.

## 스물일곱 번째 업데이트 — "자연스러운 칼선이 옵션이 아니라 기본이 되어야해"

**요청 (그대로)**: 위 스물여섯 번째 업데이트에서 "굴곡이 촘촘한 캐릭터는 여전히 살짝
오르락내리락한다"는 한계를 남겨두고 "옵션으로 만들 수 있다"고 여쭤봤는데, 답은 "자연스러운
칼선이 중요해 옵션이 아니라 기본이 되어야해" -- 선택이 아니라 기본 동작 자체를 매끄럽게 바꿔야
한다는 뜻으로 확정.

**추가로 실제 파일 9개를 새로 보내주심**(기존 12칸 시트 1개 + 새로 받은 8개, 서로 다른 캐릭터/구도)
-- 전부 스크래치 폴더에서만 열어 이번 수정 검증에 사용, 확인 직후 전부 삭제.

**문제 재확인**: 기존 12칸 시트의 "귀 여러 개" 캐릭터로 presmooth 크기를 margin의 1배, 2배, 3배,
4배, 6배, 8배까지 실제로 하나씩 늘려보며 직접 눈으로 비교. margin의 1~2배까지는 잔물결이 거의 그대로
남았고, **margin의 6배**에서 처음으로 눈에 보이는 잔물결이 완전히 사라지고 매끈하게 흐르는 곡선이
됨(8배와 비교해도 모양 차이는 미미해서 6배가 적정선).

**새로 발견한 위험**: 그런데 이 큰 presmooth 값을 한 칸 안의 모든 조각(큰 캐릭터 + 옆의 작은
말풍선/아이콘/모서리 표시)에 똑같이 적용해보니, **작은 조각들이 통째로 사라지는** 부작용이 실측으로
확인됨(반지름 14~17px짜리 작은 요소에 85px짜리 presmooth를 그대로 쓰면 buffer(+)/buffer(-)
라운드트립 자체가 그 작은 모양을 지워버림 -- 스물여섯 번째 업데이트에서 막 살려낸 문제가 다른
경로로 다시 생길 뻔함). **고침**: `core/cutline_core.py`에 새 함수
`smooth_design_naturally(design, presmooth_px, cap_factor=0.4)`를 추가 -- 여러 조각으로 이루어진
도안을 하나로 합쳐서 한꺼번에 다듬지 않고, **조각마다 따로** 다듬으면서 각 조각이 자기 크기(면적
기준 등가 반지름)보다 큰 presmooth를 쓰지 않도록 스스로 낮춤. 큰 캐릭터는 원하는 크기(margin의
6배) 그대로 매끈해지고, 작은 조각은 사라지지 않고 자기 크기 안에서만 살짝 다듬어짐 -- 실제 파일로
재검증: 말풍선/아이콘/모서리 표시 5개 전부 살아있으면서 큰 캐릭터의 곡선은 확실히 매끈해짐(면적
변화 1% 이내).

**고침 -- 조건 없는 기본값으로 확정**: `core/image_style.py`(유테)와
`core/interactive_cutline.py`(완칼/도무송) 양쪽 모두, presmooth 크기를 `margin_mm(또는 safety_mm)의
6배`로 고정하고 `smooth_design_naturally`를 무조건 적용 -- 옵션이나 토글 없이 기본 동작 자체로
바뀜.

**폭넓게 검증**: 기존 12칸 시트 재검증(눈으로 확인: 캐릭터 곡선이 매끈해지고 작은 요소 5개 전부
유지, 처리 시간 12칸 전체 14초로 여전히 60초 이내) + 새로 받은 8개 파일 중 하나(복잡한 반복 시트 --
캐릭터 여러 마리 + 하트/이파리 장식이 흩어진 배경)로 한 구역을 직접 잘라 같은 코드로 돌려봄: 캐릭터
4마리 + 작은 하트 장식 2개까지 전부 각자 매끈한 곡선으로 분리됨, 1.2초 만에 처리. 회귀 테스트 22개
전부 재실행해 통과 확인.

**검증(정리 확인)**: 위에서 새로 연 실제 파일 9개(원래 있던 것 1개 + 새로 받은 8개) 전부 스크래치
폴더 안에서만 열었고, 이번 확인이 끝난 뒤 `rm -rf`로 전부 삭제 + `git status --short`와 파일명
검색으로 레포에 아무 것도 안 들어갔는지 재확인.

**전달**: 코드(`core/cutline_core.py`, `core/image_style.py`, `core/interactive_cutline.py`) + 이
일지.

5. "잘 생선된 칼선을 복제해서 재배치 하면 된다고 했는데 왜 새로 생성해서 이중 칼선을 만들었어"
7. "도뭉송 칼선은 왜 안쪽으로 배치 되지 않고 직접하려면 커다란 사각형이 돼"

**재현 방법**: 실제 파일 하나(재단선 레이어에 실제로 10칸이 그려진 반복 패턴 시트, 표준 규칙대로
스크래치 폴더에서만 열고 분석 후 즉시 삭제)로, GUI가 실제로 호출하는 코드(`generate_cutline_by_
style`, `generate_cutline_for_selection`, `group_identical_boxes_px`, `build_cutline_design`)를
직접 그대로 돌려 각 항목을 하나씩 확인.

**2번(상태 표시줄 문구) -- 고침**: `gui/app.py`의 파일 로드 완료 메시지가 격자 설명까지 한 문장에
다 이어붙여 화면에서 길게 잘려 보이던 것을 "불러옴: N칸 인식" (격자 없으면 "불러옴: 로드 완료")
정도의 짧은 문구로 줄임. 어떤 버튼이 무엇을 하는지는 버튼 이름 자체로 충분해 별도 팝업으로 옮기지
않고 그냥 없앰.

**5번(반복 복제 대신 새로 생성돼 이중 칼선) -- 고침**: 실제 파일의 반복 행(row)들을 실측해보니
내용은 완전히 동일(축소본 픽셀 차이 0.6~1.5, 6.0 기준 대비 훨씬 작음)한데도, 작가가 실제로 그려둔
격자 칸의 높이가 행마다 945/947/941px처럼 몇 px씩 자연스럽게 들쭉날쭉해서, 반복 감지 함수
(`core.multi_design.group_identical_boxes_px`)의 크기 허용치(`max_size_diff_px=2.0`)를 넘어
"반복이 아님"으로 잘못 판정되고 있었다. 실측된 진짜 반복 사이의 최대 크기 차이(6px)에 여유를 두고
8.0으로 올림 -- 내용 비교가 여전히 1차 기준이라 크기만 비슷하고 내용이 실제로 다른 도안까지 잘못
묶이는 부작용은 없음. 고친 뒤 실제 파일로 재확인: 이전엔 3개 반복 행 중 1개가 그룹에서 빠졌는데,
지금은 3개 모두 한 그룹으로 묶여 대표 칼선 하나만 생성되고 나머지는 복제됨.

**7번(도무송 직접 하면 커다란 사각형) -- 고침**: 원인은 `core/cutline_types.py`의
`build_cutline_design`이, 선택 영역 안에 서로 떨어진 캐릭터가 여러 개 있을 때(실제 재단선 격자
한 칸에 캐릭터 4~5개가 나란히 있는 실제 구성) 그 여러 조각을 통째로 감싸는 하나의 bbox로 도형
하나를 만들어버린 것 -- 실측으로 선택 영역 면적의 88.6%에 달하는 "커다란 사각형"이 나오는 걸
직접 확인함. 완칼/유테는 이미 조각마다 따로 실루엣을 그리는데 도무송만 그렇지 않았던 차이.
이제 도무송도 서로 떨어진 조각마다 자기 bbox에 딱 맞는 도형을 각각 만들도록 고침(조각이 1개뿐인
평범한 경우는 예전과 완전히 동일 -- 회귀 없음).

**3번(다중 칼선) -- 부분적으로만 고침, 한계 있음**: 실제 파일을 직접 재현해보니, 캐릭터 얼굴 안의
눈(흰 눈동자+검은 동공) 부분이 그 둘레를 두른 얇은 윤곽선 획 때문에 몸통 본체와 완전히 끊어진
별도의 작은 섬으로 나와, 몸통 외곽선과 안 이어진 눈 모양의 작은 고리가 하나 더 뜨는 것을 실제로
확인함(실측: 면적 약 3065px^2, 몸통 79648px^2와의 거리 약 6.9px). `core/segmentation.py`의
조각 유지/버림 판정을 "절대 크기"가 아니라 "거리"만으로 다시 정리해서(이 프로젝트에서 지금까지
확인된 진짜 독립 요소는 항상 34px 이상 떨어져 있었음 -- 그보다 훨씬 가까운 20px 이내는 크기와
무관하게 같은 캐릭터의 내부 디테일로 보고 버림) 이 사례는 고쳤다. 다만 같은 파일의 다른 캐릭터
인스턴스에서는 같은 종류의 눈 섬이 몸통과 약 35px 떨어져 나오는 경우도 실측으로 확인됐는데, 이건
이 프로젝트가 지난 업데이트에서 실제로 확인/보호해둔 "진짜 독립 요소" 최소 거리(34px)와 거의
겹쳐서, 거리 기준만으로는 둘을 안전하게 구분할 수 없다 -- 더 넓히면 진짜 독립된 작은 요소(말풍선
옆 아이콘 등)를 잘못 지울 위험이 생김. 그래서 이번엔 확실한 사례(20px 이내)만 고치고, 더 먼
사례는 안전하게 그대로 남겨뒀다. 정직하게 말하면 이 특정 파일에서 일부 캐릭터는 여전히 작은
눈 모양 고리가 하나 더 보일 수 있다.

**1번(배경색을 칼선 작업함)/4번(햄스터 모자 칼선 없음) -- 아직 못 고침, 원인은 확인함**: 실제
파일로 두 가지를 각각 재현/확인:
- 한 캐릭터가 회색 배경 소품(모자를 쓴 채 기대는 받침대 같은 도형) 위에 앉아 있는 자리를 실제로
  재현해보니, 실루엣 추적(GrabCut)이 캐릭터가 아니라 그 회색 배경 도형 전체를 "이 자리의 도안"으로
  잡아, 칼선이 배경 도형 가장자리를 따라 그려지고 있었다(실측: 캐릭터+모자는 회색 도형 안에 파묻힌
  채로 하나의 큰 덩어리에 섞여 나옴).
- 같은 재현에서, 한 캐릭터의 머리/털 부분이 실루엣 추적 결과에서 통째로 빠져 있는 것도 확인함(몸통
  +옷 부분만 잡히고 머리는 아예 도안으로 안 잡힘) -- 실제 재단선 격자 한 칸이 "캐릭터 하나"가
  아니라 "캐릭터 여러 개가 나란히 있는 한 행"이다 보니, 그 큰 선택 영역의 가장자리 쪽(칸 위쪽 등)에
  가까이 있는 내용이 실루엣 추적에서 통째로 배경으로 오인되는 것으로 보임.

두 문제 다 근본 원인은 같다 -- 지금 구조는 "재단선 격자 한 칸 = 도안 하나"로 보고 그 칸 전체를
한 번에 실루엣 추적기에 넘기는데, 이 파일처럼 한 칸 안에 실제로는 서로 떨어진 캐릭터가 여러 개
있으면 추적기가 헷갈린다(배경 소품을 도안으로 잘못 잡거나, 칸 가장자리에 가까운 내용을 배경으로
잘못 지움). 이걸 안전하게 고치려면 "한 칸을 캐릭터별로 먼저 쪼갠 뒤 각각 따로 추적"하는 방식이
필요한데, 이 방식(`_expand_grid_cells_into_sub_elements`)은 이전에 다른 실제 파일에서 정상 카드형
도안을 엉뚱하게 쪼개버리는 회귀를 내서 이미 한 번 되돌린 적이 있다(열한 번째 업데이트). 충분한
검증 없이 다시 켜는 건 위험하다고 판단해 오늘은 손대지 않았고, 대신 원인만 확실히 확인해 정직하게
보고함 -- 다음 업데이트에서 더 신중하게(예: 정말로 서로 멀리 떨어진 경우에만 쪼개는 안전장치를
추가해서) 다시 다뤄야 함.

**검증**: 위 수정 4건(2/5/7/3번 일부) 적용 후 회귀 테스트 22개 전부 재실행해 통과 확인. 이번에 연
실제 파일은 스크래치 폴더에서만 열었고, 확인이 끝난 뒤 `rm -rf`로 즉시 삭제 + `git status --short`
와 파일명 검색으로 레포에 아무 것도 안 들어갔는지 재확인.

**전달**: 코드(`core/segmentation.py`, `core/multi_design.py`, `core/cutline_types.py`,
`gui/app.py`) + 이 일지.

## 서른 번째 업데이트 — 4번(햄스터 모자 칼선 없음) 원인 더 정밀하게 재조사, 시도한 수정 2건은 모두 되돌림

**배경**: "진행해" 지시에 따라 위에서 남겨둔 1번/4번을 계속 조사. 4번(캐릭터 머리/털이 실루엣
추적에서 통째로 빠짐)을 다시 실제 파일로 파고들어보니, 스물아홉 번째 업데이트에서 적어둔 "칸
가장자리에 가까운 내용이라 배경으로 오인"이라는 추측은 실제로는 틀렸다는 게 확인됨 -- grabCut에
넘기는 사각형(inner rect) 자체가 이미 칸 전체라서, 머리가 가장자리에 있다고 특별히 더 배경으로
취급될 이유가 없었음.

**진짜 원인(실측으로 확인)**: `core/segmentation.py`의 `max_grabcut_dim`(속도를 위해 grabCut 자체는
420px로 축소한 사본에서 돌리는 최적화, 2026-09-07(6차)에 추가됨) 때문이었다. 실제 크롭(1853x985px)을
420px로 축소하면, 배경(노란 줄무늬)과 색이 비슷한(둘 다 노란-주황 계열) 캐릭터의 복슬복슬한 머리
부분의 색 차이 신호가 옅어져서 grabCut이 그 부분을 통째로 배경으로 오인함을 실측으로 확인(420px:
머리 빠짐 / 원본 해상도: 머리 정상적으로 잡힘).

**시도 1 -- `max_grabcut_dim`을 420 -> 800으로 올림**: 이 문제는 고쳐졌지만(실제 파일로 확인,
머리 포함해서 깨끗하게 잡힘), 이미 이번 세션 초반에 검증해둔 다른 실제 파일(12칸 시트, 스물여섯
번째 업데이트에서 작은 장식 요소 5개를 되살린 그 파일)의 한 칸(말풍선+아이콘+모서리 표시가 촘촘한
칸)에서 같은 선택 영역을 여러 번 다시 돌려보니 결과가 불안정해짐을 발견 -- 어떤 때는 깨끗하게(작은
표시 4개 정상), 어떤 때는 작은 요소가 11개까지 과도하게 쪼개짐(grabCut 자체의 반복 최적화가 크기에
따라 서로 다른 지점에 수렴하는 비선형적 특성 때문, 실측으로 재현). 이미 검증해둔 다른 실제 파일을
새로 불안정하게 만드는 것이라 판단해 되돌림.

**시도 2 -- 선택 영역 중앙에 "확실한 전경" 시드를 추가로 줌(grabCut의 GC_INIT_WITH_MASK 방식)**:
머리 문제는 고쳐졌지만(실측), 캐릭터 여러 개가 나란히 있는 칸에서는 그 "확실한 전경" 영역이 너무
넓어서 캐릭터 사이 배경 틈까지 덮어버려, 원래 8개로 잘 나뉘던 캐릭터가 전부 하나의 큰 덩어리로
합쳐짐(실측: 캐릭터 8개 -> 1개). 이건 이 프로젝트의 핵심 요구사항(캐릭터별로 각각 칼선)을 정면으로
어기는 것이라 되돌림.

**결론**: 4번의 원인은 이제 정확히 알지만(배경과 색이 비슷한 머리/털이 속도 최적화 축소 과정에서
지워짐), 이미 검증해둔 다른 실제 파일을 깨지 않으면서 이걸 고치는 안전한 방법은 오늘 찾지 못했다.
두 시도 모두 코드에 남기지 않고 원래 상태(`max_grabcut_dim=420`, 시드 없음)로 되돌렸다 -- 정직하게
"원인은 알지만 아직 안전한 해결책이 없다"로 남겨둠. 1번(배경 소품이 도안으로 잡힘)도 같은 이유로
아직 미해결.

**검증**: 되돌린 뒤 회귀 테스트 22개 전부 재실행해 통과 확인. 이번에 연 실제 파일(현재 작업 중인
10칸 파일 + 이미 갖고 있던 12칸 파일)도 스크래치 폴더에서만 열었고, 확인이 끝난 뒤 `rm -rf`로 즉시
삭제 + `git status --short`와 파일명 검색으로 레포에 아무 것도 안 들어갔는지 재확인.

**전달**: 코드(`core/segmentation.py`의 문서 주석만 갱신, 동작은 원래와 동일) + 이 일지.

## 서른한 번째 업데이트 — "오늘 시간을 들여서 고치자": 더 근본적인 숨은 버그(결과가 가끔 달라짐)를
발견해 고침, 1번/4번은 새 시도도 부작용이 있어 되돌리고 여전히 미해결로 남김

**배경**: "오늘 시간을 들여서 고치자" 지시에 따라 1번/4번을 계속 조사.

**새로 발견한 문제(1번/4번과는 별개, 더 근본적)**: `segment_design_in_region`이 쓰는
`cv2.grabCut`은 내부적으로 OpenCV의 전역 난수 생성기(RNG, 색 분포를 K-means로 초기 분류할 때
사용)를 쓰는데, 이 RNG는 시드를 고정해주지 않으면 "지금 켜져 있는 프로그램에서 grabCut이 몇
번째로 호출됐는지"에 따라 매번 다른 상태에서 시작한다. 그래서 재단선 격자 한 칸의 크롭 픽셀이
완전히 똑같아도, 그 프로그램 실행 중에 그 앞에서 grabCut이 몇 번 더 호출됐었는지에 따라 같은
칸의 결과가 달라질 수 있음을 실제 파일로 확인함 -- 한 칸을 완전히 새로 켠 프로그램에서 격리해서
여러 번 돌리면 매번 똑같이 나오지만, 같은 프로그램 실행 안에서 다른 칼선 작업을 몇 번 먼저 시키고
나서 그 칸을 돌리면 조각 수가 7개에서 53개까지 늘어나며 지저분해지는 경우를 실측으로 확인함.
이건 "가끔 운 나쁘면 같은 파일도 다르게 나오는" 진짜 문제라서, 매 grabCut 호출 직전에 항상 같은
시드(`GRABCUT_RNG_SEED`)로 되돌리도록 고쳤다 -- 몇 번째 호출이든 같은 크롭에는 항상 같은 결과가
나오게 고정. 이미 검증해둔 실제 파일 2개(10칸/12칸) 전체 칸에서 회귀 없이 안전함을 확인했고
(오히려 이 시드 값 자체로 일부 칸이 더 깨끗해지는 부수 효과도 있었음), 회귀 테스트 22개도 재실행해
통과 확인.

**1번/4번 자체를 고치려는 새 시도**: "칸 전체를 먼저 대충 한 번 훑고(1차), 조각이 여러 개로
나뉘면 각 조각만 따로 타이트하게 다시 크롭해서 재추적(2차, 정제)"하는 2단계 방식을 새로 만들어
시도함. 조각이 1개뿐이면(캐릭터 하나만 있는 흔한 경우) 기존과 완전히 동일하게 두어 회귀 위험이
없게 설계함. 실제 파일로 테스트해보니:
  - 처음엔 정제 과정이 바로 옆에 있던 "원래부터 따로 떨어져 있던 작은 장식 요소"(예: 아이콘,
    모서리 표시)까지 다시 삼켜버리는 회귀가 발견됨 -> 정제 결과가 다른 원래 조각과 겹치면 버리고
    원래 조각을 쓰는 안전장치를 추가해서 고침.
  - 그 다음엔 장식 요소 하나만 딱 떨어져 있어 다른 조각과는 안 겹치는 경우에도, 너무 좁게 다시
    자른 크롭 안에서는 색 정보가 부족해 grabCut이 배경까지 도안으로 삼켜버리는(면적이 39%나
    늘어남) 새 문제가 발견됨 -> 정제로 면적이 30% 넘게 늘어나면 버리고 원래 조각을 쓰는 안전장치를
    추가해서 고침.
  - 위 두 안전장치를 다 넣은 뒤 다시 실제 파일 전체로 비교해보니, 이번엔 또 다른 부작용이
    발견됨: 이미 깨끗하게 한 조각으로 잘 잡히던 캐릭터를 굳이 다시 재추적하는 과정에서, 외곽선이
    지저분하게 여러 갈래로 갈라지는 경우가 실측으로 확인됨(예: 이미 매끈했던 캐릭터 외곽선이
    재추적 후 얼굴을 가로지르는 지저분한 선들로 깨짐). 이건 "원래 이미 좋았던 결과를 다시 손대서
    오히려 나빠지는" 경우라, 세 번째 부작용까지는 오늘 안에 안전하게 고칠 방법을 찾지 못함.

**결론**: 정직하게, 이 2단계 정제 방식은 오늘은 코드에 남기지 않고 완전히 되돌렸다. 1번(배경
소품이 캐릭터와 함께 도안으로 잡힘)과 4번(배경과 색이 비슷한 머리/털이 빠짐)은 오늘도 여전히
미해결로 남는다 -- 대신, 이 둘을 고치려다가 우연히 발견한 "결과가 프로그램 실행 히스토리에 따라
가끔 달라지는" 문제는 오늘 확실하게 고쳤다. 이건 1번/4번보다 더 근본적이고, 눈에 잘 안 보이게
아무 파일에서나 가끔씩 나타날 수 있는 문제였어서, 오늘 손댄 것 중 가장 값어치 있는 수정이라고
생각한다.

**검증**: 새 시드 고정 수정 적용 후 회귀 테스트 22개(이 중 tkinter가 없는 이 작업 환경에서
못 돌린 GUI 연동 테스트 몇 개 제외) 전부 재실행해 통과 확인. 실제 파일 2개(10칸/12칸) 전체 칸을
새 프로그램 실행마다 새로 돌려 old/new 비교 재검증(격리되지 않은 반복 호출 방식은 방금 발견한
RNG 오염 문제 때문에 비교 방법 자체가 잘못됐었다는 것도 이번에 확인 -- 매번 새 프로그램으로
격리해서 비교하는 방식으로 바꿔 재검증함). 이번에 연 실제 파일은 스크래치 폴더에서만 열었고,
확인이 끝난 뒤 `rm -rf`로 즉시 삭제 + `git status --short`와 파일명 검색으로 레포에 아무 것도
안 들어갔는지 재확인.
